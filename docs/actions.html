Actions Subsystem

Named commands and the controls that present them

All manuals

Introduction

An Action is a named command: its text, its icon, the work it runs, and whether it is currently available. Save, Copy and Reload are examples. One action serves any number of controls - a toolbar button, a menu item, a keyboard shortcut - and all of them show the same state, because they all read one object.

Module Import: 
import ClaFi.Core.Foundation;

An action involves two roles:

  • The presenter is the control that shows the action, such as the button in the toolbar or the item in the menu. It displays the action's text, tooltip and icon, shows its state, and delivers the click. The caller attaches it.
  • The subject is the control the action acts on, such as the text box Copy copies from. The caller does not attach it: the action finds it, because the user chose it by placing the focus there.

Many actions have no subject: Save acts on a document, not on a control. When no control claims the action, the action's own handler runs, so no subject is needed.

An action stores no state. Its enabled and selected state belongs to the control it acts on, so both are queried whenever they are needed.

Basic Usage Example

An action is an ordinary object. Store it wherever the object it acts on is stored - a window class is the usual place - and pass it to as many controls as needed:

// a member of the window, next to the document it acts on. The window's scope owns it
// and hands back a reference, so declaring it and putting its key in reach are one line.
Action& m_save{ actions().add(
    Text{ L"Save" },
    TooltipText{ L"Write the document to disk" },
    Shortcut{ L'S', { .ctrl = true } },
    Events{
        [this](ActionClickEvent&) { m_document.save(); },
        [this](GetActionStateEvent& event) {
            event.claim({ .enabled = m_document.modified() });
        },
    }
) };

// ...and in the window's constructor
toolbar.add<Button>(m_save, ButtonViewMode::IconOnly);   // a presenter
menu.add<MenuItem>(m_save);                          // and another

The button shows "Save", is disabled while the document is unmodified, and saves when clicked. The menu item does the same and prints Ctrl+S in its shortcut column. The key works whether either of them is on screen.

Giving an Action to a Control

Who Owns an Action

The scope the action is added to owns it, which is the ordinary case. The action belongs to that window and is destroyed with it. add returns a reference for the caller to keep, so one line both creates the action and registers its shortcut.

An action owned elsewhere - by a document, or shared between two windows - is registered instead of created:

actions().add(m_document.saveAction);
Registering an action is what makes its shortcut work. Attaching an action to a button does not register it: a shortcut bound to a control stops working when that control is scrolled out of view or its menu is closed. An action created by add is already registered; one owned elsewhere is registered only when the caller registers it. See Scopes.

Handing It to a Control

An action is a construction property, so a control receives one the way it receives a text:

toolbar.add<Button>(m_save, ButtonViewMode::LeftIcon);

The action can also be attached after construction, and detached again:

m_save.attach(someButton);
m_save.detach(someButton);

What the Control Takes From It

The action'sBecomes the presenter's
text()Text, written into the control when the action is attached, and only if the control has none of its own.
tooltipText()The tooltip's body, under the caption and the key the presenter states.
OnDrawIconIcon, wherever the control paints one.
stateEnabled and selected.
-A click on the presenter runs the action.
shortcut()The key the presenter shows in the tooltip's caption line, and that a menu line prints at its end.
A tooltip has a caption and a body. The caption and the key appear in one bold line above the body, and the TooltipText is the body below it. The presenter states the caption and the key: a button states its own caption and the key that runs it, and a menu line states neither because the line prints both. A tooltip appears when either part is present; a button that draws its caption and has no key and no body shows none.
A control's own text takes precedence. The action supplies text only to a presenter that has none. A presenter that sets its own text keeps it. The decision is made when the two attach: a control given the action as a property attaches once its own text is bound, and attach called afterwards reads whatever the control's text is at that point.

The Presenter's Role

A PresenterRole property states what the control does for the action, and a control that states no role takes Button:

RoleWhat the presenter does
ButtonDelivers the click, and shows only the command's face: the icon, and the name where the control has no text of its own. Its tooltip states the caption and the key over the body.
LineDelivers the click, and writes the name and the key itself - a menu line. Its tooltip carries a stated TooltipText as the body and no caption, since the line already shows both.
DisplayShows the command without delivering it. A split button's face uses this role: its press belongs to the button that routes it.
OpenerWrites the name itself and opens the command's own list instead of delivering the command - the line a menu shows for a command holding commands, see below. Its tooltip is that of a Line.

What a Presenter Has to Be

Do

  • Give a presenter NavigationReach::No and MouseFocus::Keep when its action has a subject, so neither a key nor a press moves the focus to it - see Selection and Focus.
  • Leave menu items unchanged: a menu press does not move the focus, so a menu item needs neither property.

Don't

  • Make a subject-taking presenter focusable. Pressing it moves the focus off the subject, so the action resolves to the button itself or to nothing, and that press disables the button.
  • Attach to a control that is never clicked; see below.
A presenter that is not interactive - isInteractive() returns false, as for a label - never delivers a click, so attaching an action to it is an error. The error is reported on that control's first state query, which happens before its first paint, with noReach("An action was attached to a control that never delivers a click"), which throws std::logic_error.

State

An action's state is ActionState: enabled and selected. It is computed by asking in this order, and the last state reported is used:

  1. The first control that claims the action, walking up from the focused control, supplies the state.
  2. If no control claims it, the action's own GetActionStateEvent handler supplies the state.
  3. If neither supplies one, the action is enabled if it has anything to run.

A state handler is optional. An action that carries its own work and reports nothing about when it is available is enabled by default.

Control::canClick already tests enabled, so a disabled action's presenter does not deliver a click, and no code tests the state.

Saying the Answer Changed

The action stores no state, so the state cannot go stale on its own. A presenter, though, has already been painted with the state from its last query. Three calls report what changed:

CallWhen
invalidateState()What the action tests has changed, so enabled or selected may be different. Every presenter is asked again and animates to the new state.
invalidate()The icon would draw something new.
invalidateText()The text changed: every presenter that holds the action's text receives it again, and the size the presenter asked for is stale.
void Window::documentChanged()
{
    m_save.invalidateState();
}

Answering an Action

A control becomes a subject by answering two events. Any control can do this; the connectors are on Control.

Claiming

GetActionStateEvent is asked of every control, starting at the focused one and moving up the parent chain. A control claims the action to report that the action applies to it, and the first control that claims is the subject, which is also the control that receives the click.

The claim is a separate statement from the state it reports:

event.claim({ .enabled = hasSelection() });

Do

  • Claim an action the control understands even when it cannot run it right now, and report it disabled. A text box with nothing selected is still the subject of Cut.
  • Answer ActionClickEvent for exactly the actions the control claims.

Don't

  • Skip the claim because the control cannot act. The action then passes to whatever is further up the chain, which answers for a control the user is not in.
  • Do work in the state pass. The pass runs on every state invalidation, so it should only test.

Worked Example: TextBox

The framework's own subject is the text box. Its constructor calls connectEditActions, which connects both handlers:

onGetActionState([this](GetActionStateEvent& event) {
    const bool hasSelection = m_editProps.selRange.length != 0;
    if (&event.action == &StdActions::cut)
        event.claim({ .enabled = hasSelection });
    else if (&event.action == &StdActions::copy)
        event.claim({ .enabled = !text().plainText().empty() });
    else if (&event.action == &StdActions::paste)
        event.claim({ .enabled = !clp.empty() || Platform::clipboardHasText() });
    else if (&event.action == &StdActions::del)
        event.claim({ .enabled = hasSelection });
});

onActionClick([this](ActionClickEvent& event) {
    if (&event.action == &StdActions::cut)
        cutSelectedText();
    else if (&event.action == &StdActions::copy)
        copySelectedText();
    else if (&event.action == &StdActions::paste)
        pasteClipboardText();
    else if (&event.action == &StdActions::del)
        deleteSelectedText();
});

An action is identified by its address. The subsystem has no ids, no tags and no type tests, so the actions a framework control answers are objects the framework owns - see below.

Shortcuts

Declaring One

Shortcut{ L'S', { .ctrl = true } }        // Ctrl+S
Shortcut{ vkF2 }                          // F2, no modifiers
Shortcut{ vkDelete, { .shift = true } }   // Shift+Delete

The virtual key code of a letter is its own uppercase character, so L'S' is the key marked S. Shortcut::text() renders the shortcut as the user's keyboard labels it, modifiers included, so a German layout reads Strg+S without any layout code in the application.

More Than One Key

An action accepts any number of shortcuts, and each of them runs it. The first is the one shown: a menu line and a tooltip show that one, and the others also run the action.

Action m_closeTab{
    Text{ L"Close tab" },
    Shortcut{ L'W', { .ctrl = true } },        // Ctrl+W, the one shown
    Shortcut{ Keys::F4, { .ctrl = true } }      // Ctrl+F4
};

addShortcut() puts one more key after the ones an action has, and setShortcut() makes the key it is given the only one - so setShortcut({}) leaves the action with none.

Scopes, and the Order They Are Asked

A shortcut belongs to a scope, not to a control. Bound to a control, it would stop working when that control was scrolled away or its menu closed. There are two scopes:

actions()                    // on a form - the commands that belong to this window
AppActions::get()          // the application's, and where the standard actions are registered

A key is looked up in this order:

  1. The key is offered to the control that holds the focus, then to each of its parents.
  2. The form's scope is asked next.
  3. The application's scope is asked after that.
  4. The focus navigator is asked last.

A control that handles the key itself takes precedence: a shortcut applies only when no other meaning does. A disabled action does not consume the key, so the next scope can still answer, and a second action sharing the shortcut can run too.

While a popup is open, the popup receives the key. The popup uses the same pipeline: its own scope is queried first, then the application's. The form behind it does not receive the key, because the popup is the window that takes input.

The Framework's Own Actions

Cut, copy, paste, delete, select all, undo and redo are objects the framework owns. They are in ClaFi.StdActions, in the StdActions namespace:

import ClaFi.StdActions;

StdActions::cut;
StdActions::copy;
StdActions::paste;
StdActions::del;          // Delete. Spelt short because `delete` is a keyword
StdActions::selectAll;
StdActions::undo;         // Ctrl+Z
StdActions::redo;         // Ctrl+Y, Ctrl+Shift+Z

ApplicationBase::initialize calls StdActions::registerAll(), which puts all seven in the application's scope. Every application gets the standard keys from that call; an application that needs a key for itself clears that action's shortcut.

They are above Core because an action holds an icon. AppActions is the scope and stays in Core, which cannot see Icons. Delete holds Icons::DeleteIcon, so a button or a menu item that presents it draws that icon without any icon code. drawDocumentDelete and drawSettingsDelete place a red X over the subject that a permanent-delete confirmation removes.
Delete has the Delete key, and a control whose Delete key means more than the command keeps the key. A text box with nothing selected deletes forward, by a character or by a word, so it handles that key itself. The action removes the selection; its menu item and its toolbar button run the command.
Undo and redo state only the direction. What one step is, and how many steps there are, belong to the subject: a text box keeps its own history and reports whether there is anything to undo or redo. A control that keeps no history claims neither action, so the keys fall through to whatever does.

They are ordinary objects. Translate them, give them icons, or clear their shortcuts by writing to them:

StdActions::copy.text().clear();
StdActions::copy.text() << tr(L"Copy");
StdActions::copy.setShortcut({});   // and now Ctrl+C is yours to use

Adding one to a menu is the same as adding any action:

editMenu.add<MenuItem>(StdActions::copy);

They work on whatever text box has the focus, including one a grid opened for in-place editing, because the subject is found rather than wired.

A command that framework controls answer is a framework object. Any other action belongs to the application: the application declares the action and writes the control side that answers it, so both ends use the same object. A context menu that needs its own wording declares its own action rather than a second Copy.

Writing an Action of Your Own

When no control claims the action, its own handler is the implementation and no subject is involved:

Action m_reload{
    Text{ L"Reload" },
    Shortcut{ vkF5 },
    OnEvent{ [this](ActionClickEvent&) { reload(); } },
};

For an action that acts on whatever control the user is in, write both sides - the action, and the answer in the control:

// the action, held by the window
Action m_zoomIn{ Text{ L"Zoom in" }, Shortcut{ L'=', { .ctrl = true } } };

// the answer, in the view that can zoom - it sees the same object
view.onGetActionState([&](GetActionStateEvent& event) {
    if (&event.action == &m_zoomIn)
        event.claim({ .enabled = view.canZoomIn() });
});
view.onActionClick([&](ActionClickEvent& event) {
    if (&event.action == &m_zoomIn)
        view.zoomIn();
});

Two views written this way share one action, and whichever one the user is in answers it.

An Action cannot be copied or moved - every connection it holds captures its address. Hold it by value as a member, or let a scope own it with actions().add(...), which returns a reference. Never put actions in a container that reallocates.

A Command Holding Commands

An action holds a list of actions with setItems, where a null parts two groups as it does in a context menu's list. A menu given such an action shows it as a line with the list beside it: the list opens when the pointer rests on the line, when the line is pressed, and on Right, and it closes when the pointer rests on another line, on Left and on Escape. A command run in the list closes every menu the list stands beside, and a list holds lines of its own the same way. The holding command's own click is not run, because its line presents it in the Opener role, and its state grays the line like any other.

Action kind{ Text{ L"Kind" } };
Action asFolder{ Text{ L"Folder" } };
Action asPage{ Text{ L"Page" } };
kind.setItems({ &asFolder, &asPage });

// on the subject: the lines of the list resolve to it through the menu they stand beside
view.onGetActionState([&](GetActionStateEvent& event) {
    if (&event.action == &asFolder)
        event.claim({ .selected = view.isFolder() });
});

How It Works

Resolving the Subject

The search starts at the control the focus is on and continues up the parent chain - the same path a key takes. Where a container holds the focus for an item inside it, the search starts at that item, so a text box on a page claims Select All ahead of the page. Each control is asked GetActionStateEvent, and the first control that claims ends the search. A control with no handler for that event is skipped without an event being built, so a form of ordinary controls costs one pointer chase per level.

The search runs when a state is invalidated, not once per frame, and again when the action is run. Nothing is stored, so two calls a frame apart may return a different state, because the state belongs to whatever control the user is in now.

Because a menu press does not move the focus, a menu item's action resolves to the control in the window behind it without any code for that. A popup opened on a line of another popup - a list beside a menu - resolves through that popup to the control it was opened on, down to the form, which is not a popup, so a line of the list reaches the same subject the menu's lines do.

Attachments and Lifetime

The action holds a list of its presenters. A presenter stores nothing for the action, and neither does a subject: Control has no member for it. Attaching connects handlers on the presenter's own dispatcher, records the connections, and writes the action's text into a presenter that has none. Detaching removes the connections, so a part handed to another action next uses that action's text.

The action and a presenter can be destroyed in either order. When a presenter is destroyed - a menu rebuilt, a toolbar repopulated - ~Control emits DestroyEvent and the action drops that attachment. When the action is destroyed first, it disconnects from every presenter still alive and removes its text from the presenters it supplied.

A subject needs none of this: it is found by a search rather than registered, so destroying one leaves nothing to undo.

Two Events, and Identity by Address

The subsystem reports an action's state and click through GetActionStateEvent and ActionClickEvent, and defines no third event type for either. Every action-aware control's handler is therefore called for every action, and each handler first compares the address to decide whether the action is its own.

An event type or an id per command would make that distinction at compile time and would cost a declaration for every command in the application. Comparing addresses costs one branch in one place per control, and the framework ships two event types rather than a type per command.
