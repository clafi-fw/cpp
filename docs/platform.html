Platform and Ownership

The Windows and Wayland platform layer

All manuals

Introduction

The platform is the object an application is built against. It is the only place where the framework meets the operating system, and it holds every process-wide resource: the connection to the display server, the timers, the clipboard, and the directory watches. An application holds exactly one platform, constructs it before anything else and destroys it last, and every other object in the process - the context, the forms, each control - depends on it.

Module Import: 
import ClaFi.Platform.Windows;   // Win32Platform, Win32Application
import ClaFi.Platform.Wayland;   // WaylandPlatform, WaylandApplication

Most code never names the platform. A control reaches what it needs through its context - the clipboard through formContext().clipboard(), the animation controller through appContext().animator() - and the framework's own services reach their owner through one of two seams described in Reaching the Platform From Below.

Nothing framework-wide is a static. Every object that serves the whole process has an owner, either the platform or the application's context, and the object is constructed and destroyed at the position its owner's member order gives it. A service that cannot hold a reference to its owner - a hook with no object in hand - reaches it through a standing pointer that the owned object sets and clears. A hook that finds no pointer standing has found a broken order and reports it.

Basic Usage Example

An application is Application<Platform, GpuBackend>, or a class derived from it, constructed from the platform's Params. The second argument names the GPU backend the application offers and may be left out, which offers none. Only the entry point names the concrete platform:

// Win32 - Direct2D beside the CPU backend
int __stdcall wWinMain(HINSTANCE hInstance, HINSTANCE, wchar_t*, int)
{
    using namespace ClaFi;

    Themes_App::ThemesApplication<Win32Platform, Direct2DBackend> app{ { hInstance } };
    return app.run();
}

// Wayland - no GPU backend is named, because this platform has none
int main()
{
    using namespace ClaFi;

    Themes_App::ThemesApplication<WaylandPlatform> app{ WaylandPlatform::Params{} };
    return app.run();
}

Two aliases name the common pairings: Win32Application is Application<Win32Platform, Direct2DBackend> and WaylandApplication is Application<WaylandPlatform>. The CPU backend is the core's own and every application has it, so Application<Win32Platform> draws on the CPU and has no GPU backend to enable. An application that names Direct2D carries both and starts on whichever its config holds - see The Backend.

A platform that cannot start throws. WaylandPlatform's constructor connects to the compositor, and where there is none it throws a std::runtime_error naming what WAYLAND_DISPLAY held. Left uncaught, that ends the process with the message on stderr, the outcome expected for a client started outside a session. No probe runs before construction: building the application is the only attempt.

The Two Halves of a Platform

A platform is two classes in a base-derived pair. Platform, declared in the Context module, is the interface the rest of the framework uses and is the same on every platform. Win32Platform and WaylandPlatform derive from it, one per build, and are what the entry point names. The base declares the contract, and the derived class owns the objects that implement it.

Platform, the Neutral Half

Platform is declared in ClaFi.Core.Context.FormContext and carries three kinds of member:

KindMembersWho answers
StaticssetApplicationId, createFormsConfigSchema, restoreFormPlacement, storeFormPlacement, addFormToSession, keyName, keyModifiers, beep, globalScaleFactor, caretBlinkTime, processCpuTime, setCursor, cursor, getCursorInfo, shellExecute, pickFolder, pickSaveFile, appDataPath, documentsPath, executablePath, executableDirectory, debugOutput, systemColorMode, events Each platform supplies the bodies in its own unit - Wayland.Platform.cpp, an implementation unit of the Context module, and Windows_Facade.cppm. A static that needs the display server reaches it through a standing pointer - see The Standing Pointer.

Wayland names the optional protocols present and missing.
One owned object, by referenceclipboard() The derived platform owns the Transfer::Clipboard as a member and names it to the base at construction: Platform(Transfer::Clipboard&).

The base holds a reference rather than the clipboard itself because of construction order: a base is constructed before any member of the derived class, and on Win32 the clipboard must be constructed after the OLE apartment the windows manager opens. The derived class therefore declares the clipboard where the order requires it and passes the base its address before the clipboard is constructed. A reference may be bound that early because nothing reads through it until the platform is fully constructed.

The Platform Built for the Display Server

Win32Platform and WaylandPlatform are the owners. Each derives from Platform and from one further interface that declares what its platform layer offers to services below the context - the subject of The Empty Name and What Stands Behind It:

export struct Win32Platform
    :
    public Platform,
    public PlatformImplementation::Windows::IMessageWindowFactory
{
    ...
};

export struct WaylandPlatform
    :
    public Platform,
    public PlatformImplementation::Wayland::IDisplayAccess
{
    ...
};

Both platforms follow one rule: a platform member is declared after everything it needs and before everything that needs it. What the platform owns is reached through the platform - or, where a hook has no object in hand, through the standing pointer that the owned object publishes.

Params

Each platform declares a Params struct, and IsPlatform requires only that a platform is constructible from one. The entry point passes the struct to the platform's constructor:

PlatformParamsMeaning
Win32PlatformHINSTANCE appInstance The instance handle wWinMain is given, which every window class and window is registered under.
WaylandPlatformbool watchesClipboard{ false } Whether the application watches the clipboard rather than pastes from it. A compositor announces a selection only to the client holding the keyboard focus, so an application that displays clipboard contents sets this flag to request the clipboard manager's channel where the compositor offers one.

What the Platform Owns

C++ constructs members in declaration order and destroys them in reverse, and that rule supplies the entire lifetime mechanism here. Each platform lists its members in the order they depend on one another, and a comment on the list states the reason for each position.

Win32Platform

private:
    Params m_params;
    PlatformImplementation::Windows::WindowsManager m_manager{ m_params.appInstance };
    PlatformImplementation::Windows::TimerManager m_timers{ m_manager };
    Transfer::Clipboard m_clipboard{ *this };

Transfer::ClipboardThe clipboard, with its Windows half behind it - the IDataObject OLE holds and the listener window. Last: its destructor renders the package onto the clipboard, which requires the OLE apartment to still be open.

Order Is the Design

Basing the lifetime on member order has two consequences.

First, a platform has no initialize() or finalize(). A member's constructor initializes it and its destructor finalizes it, so a member declared in the right place needs neither call. A separate finalization step is needed only when something must happen while a later member is still constructed, and no member of either platform has that requirement: the Win32 clipboard flushes in its own destructor, which runs before the manager's destructor, and that order is the correct one.

Second, the event loop does not name the objects it polls. On Wayland the display would otherwise depend on the timer manager and the watch manager, which would put them below it in the module graph and above it in the ownership order at the same time. The display instead offers addPollSource and removePollSource, and the platform - which owns both the display and the managers - registers each descriptor through a PollSource whose lifetime is the registration.

A platform member declared in the wrong place is not caught at compile time. The member list in each facade has a comment stating the order and the reasons for it; a new member belongs in that list.

Where the Platform Stands in an Application

First Up, Last Down

Application<Platform, GpuBackend> holds its platform in a base, not a member:

template <IsPlatform PlatformType>
class PlatformHolder
{
protected:
    PlatformType m_platform;
};

export template <IsPlatform PlatformType, IsOptionalGpuBackend GpuBackend = void>
class Application : private PlatformHolder<PlatformType>, public ApplicationBase
{
    ...
};

Bases are constructed in declaration order and destroyed in reverse, so the platform is constructed before ApplicationBase - and with it the AppContext, the config and the ThemesManager with its directory watch - and destroyed after them. Every object an application owns is therefore constructed after the platform and destroyed before it. A UiTimer stopped from a destructor is stopped while the timer manager still exists; a directory watch removed from a themes manager's destructor is removed while the watch manager still exists; a form's window is destroyed while the windows manager still holds its class.

A base class enforces this order. A platform held as a member behind ApplicationBase would be constructed after the context and destroyed before it.

The Whole Lifetime

The sequence from the entry point's braces to their close is:

StepWhat happens
1PlatformHolder constructs the platform from its Params: the platform's members in their declared order, each constructed on the ones before it. The platform is fully constructed at the end of this step.
2ApplicationBase is built on it: the config path, the AppContext holding a Platform& and the GPU backend's factory where the application named one, then the ThemesManager. The manager subscribes to theme, color mode, and desktop appearance changes.
3Application's constructor body calls ApplicationBase::initialize(): the application id is stated to the platform, the standard actions and the transfer formats are registered - the paste action connecting to the platform's clipboard - the app menu is connected, the diagnostic log is built and given the platform's diagnosticLines, the initial theme is applied, and the config is read.
4The application's own members and its run(): forms are built, each asking the platform for its window and the context for a backend to draw it, and the main form's loop runs on the platform's event loop.
5The application's own members are destroyed. A form's root stops its animations while its form is still reachable; a container stops its subtree's animations before detaching the children - see Teardown.
6~Application calls finalize(): the config is saved where the user allowed it, and the diagnostic log is released. The function runs once however many times it is called, so an application whose own members the save reaches calls it from its own destructor first.
7WindowApplicationBase releases the menu action connection, the themes manager with its connections and folder watches, then the context, whose destructor stops the theme crossing.
8The platform is destroyed, its members in reverse order: the clipboard flushes or hands its selection back, the timers stop, the display or the windows manager closes.

AppContext

AppContext is what a form or a control means by "the application". It holds the platform by reference and returns it as platform(), and it owns what the application runs for itself rather than what the platform creates from the operating system: the AnimationController, as animator(), and the UpdateCheck, as updateCheck(). The animation controller belongs to the context rather than to the platform because the application owns it. It steps every fade of a control's state, every glide, and the theme crossing through one UiTimer that the platform's timer manager serves. Its owner must be constructed after the platform and before every control, which is where the context is.

The update check holds a WebFetch for the duration of a request: one request on a thread of its own, answered on the UI thread through a UiTimer. A fetch cancels its request and joins its thread in its destructor, and the context is destroyed before the platform, so the timer the fetch stops during destruction is stopped while the timer manager still exists.

A FormContext holds a const Platform& and returns the one thing a control requests from the platform directly, the clipboard, as clipboard(). The returned reference is not const: the clipboard is the process's state rather than the context's, and a copy made from a const context is still a copy.

The Backend

The platform creates a form's window; a backend draws into it. A form requests one from the context as it is constructed - AppContext::createBackend(window, size) - and receives the GPU backend the application named while GPU acceleration is on, or the CPU backend otherwise. The two kinds are constructed from different arguments, and a concept specifies each:

ConceptBuilt fromWhy
IsGpuBackend(IPlatformWindow&, IntSize) It draws into a window the platform owns, and reads the native object it needs out of that window.
IsCpuBackend(IntSize) It owns its pixel buffer, which the window presents.

Besides its size, a backend is given one property of its window: whether the window carries an alpha channel. That determines whether a frame starts cleared where the pixels outside a rounded corner are read.

The choice is made in the application's type. Application is a template and a form is not, so the choice reaches the context as a function pointer - gpuBackendFactory<GpuBackend>(), null where none was named - and AppContext::gpuAvailable() reports whether that pointer is set. Where it is set, the config's Performance section holds BackEnd, with values CPU and GPU. The default is GPU. The backend choice on the Settings page writes this value. Each window switches at the top of its next frame, and its canvas releases the resources held by the previous backend. An application without a GPU backend uses the CPU for every window.

No other part of the platform depends on which backend draws, and no part of a control does. The Graphics manual describes what the two draw and where they still differ.

Reaching the Platform From Above

Code above the context - forms, controls, an application's own pages - never names Win32Platform or WaylandPlatform. It reaches what it needs through the context it already has, and that context exposes only Platform.

Windows

A form creates its window in its own member initializer through the context's platform:

std::unique_ptr<IPlatformWindow> m_window{
    m_appContext.platform().createWindow(*this, m_windowRole, popupTargetForm())
};

createWindow is the virtual function each platform implements. The derived platform returns a FormWindow built from the object it owns - the windows manager on Win32, the display on Wayland - and passes that object to the new window, so no window obtains it elsewhere. A popup receives its parent's window the same way, through the parent form. WindowRole has three values: Dialog, Menu, or Tooltip.

Window Opacity

A window's opacity is a byte on its IPlatformWindow - alpha() and setAlpha(ColorByte) - applied to the whole window at once. A tooltip fades in and out this way, stepping the byte on AnimationSlots::FormAlpha. Each platform applies the value through the cheapest mechanism available:

PlatformWhat applies it
Win32The window's composition visual. The shadow window the form casts its shadow from takes the same value, so the two fade together. Nothing is repainted.
Wayland, where the compositor offers wp_alpha_modifier_v1The compositor, as a multiplier stated on the surface. A change is one commit - no paint, no pixel pass, no new buffer - and it applies to a buffer without an alpha channel too, so an opaque window fades the same way. While the window is off the screen the value waits in the surface's pending state for the commit that maps it.
Wayland, where it offers noneThe frame, where the window's buffer carries an alpha channel. Every pixel is written at the window's opacity, and a change repaints the window. Premultiplied color scales with its own alpha, so the four channels take one factor, the result is still premultiplied, and a rounded corner keeps the coverage it was drawn with.

On Wayland, zero takes the window off the screen on either path. A frame at zero opacity is not drawn, and a hidden tooltip is unmapped.

The Clipboard

The clipboard is formContext().clipboard(), a Transfer::Clipboard&. A copy stores a package on it with the stamp of the input event; a paste requests an offer:

// a copy, from a handler that has the click's stamp
Transfer::Source source{};
source.add<Transfer::PlainText>(selectedText());
formContext().clipboard().set(std::move(source), stamp);

// a paste
if (Transfer::Offer* offer = formContext().clipboard().offer())
{
    if (const std::optional<std::wstring> text = Transfer::take<Transfer::PlainText>(*offer))
        insert(*text);
}

// what to connect to instead of polling - scoped, because the clipboard outlives the listener
ScopedEventConnection watch{ formContext().clipboard().events()
    .connect<Transfer::ClipboardChangeEvent>([&](Transfer::ClipboardChangeEvent&) {
        refresh();
    }) };

Where only a form is at hand, form->context().clipboard() returns the same object. The clipboard's own manual is the Transfer footnote under Source/.seedocs/footnotes. One instance exists per process; it is a member of the platform, and it is constructed before the first window and destroyed after the last.

Animations

A control runs its animations through Control::animate, which reaches the application's controller through the control's form:

animate(AnimationSlots::Expander, m_expandedFactor, target, [this](AnimateParams& params) {
    m_expandedFactor = params.value;
    invalidateChevron();
});

stopAnimation(AnimationSlots::Scroll);   // one slot
stopAnimations();                           // every slot of this control

animator() returns the controller, or null while the control is in no form, since no application is reachable then. animate on a control in no form applies the end value at once through the same callback: an unattached control is not visible, and the end value is what it is drawn from once attached. A form reaches the controller as appContext().animator(); an object that is not a control - the grid's cell highlights - obtains it from the control it belongs to and handles the null the same way.

What the Platform Reports

The platform reports user input to the form whose window received it, through IForm: a pointer move, a press, a wheel, a key, or a side button. The form converts each report into the framework's input state, which is stored in Input - one instance per application rather than one per form, since focus leaves one window as it arrives in another.

The Input Controllers

The mouse and the keyboard are each an InputController, which holds whether that device drives the input and a factor that follows that state through a fade. Code outside Input reads the controllers and never writes them:

const InputController& mouse = Input::mouse();
const InputController& keyboard = Input::keyboard();

bool byKey = !mouse.active();         // whether a key did what is being handled
float ringShare = keyboard.factor();  // active() through its fade, from 0 to 1

What the form is told switches them:

ReportMouseKeyboard
A pointer move, a press or a release, a wheel, a side button, a menu asked for at a pointOnOff
A key, or a menu asked for from the keyboardOffOn
A bare modifier - Shift, Ctrl, AltAs it isOn

The both-on state therefore occurs only after a modifier and lasts until the next pointer report or key; both off cannot occur. A modifier names no destination - it qualifies the click or the key that follows, and the pointer remains where the user left it. Two reports change nothing: a held key's repeat, and the first move a form receives after the pointer enters, which only hit-tests. Win32 sends a move to a window that appears under a stationary pointer, and a Wayland enter arrives as one.

A click, or a menu opened by the pointer, always leaves the mouse controller on. A key other than a modifier leaves it off, unless the pointer moved while that key was held down and repeating.

The fades run on the application's animator, obtained through the AppContext the form reporting the input passes in, so Input owns nothing that must be released. The two slots, AnimationSlots::KeyboardActive and mouseActive, mirror each other, so a switch from one device to the other is one crossfade. Each step of either fade raises InputSwitchEvent on AppContext::events(), and every visible form repaints whole on it: the color rules read the two factors as RuleInput::Keyboard and RuleInput::Mouse, so no control is invalidated on its own. The hovered control and the focused control re-read their state as well, up to the root form through any popup between, since their Hot and Current carry the device. The Color manual describes what the rules do with them.

Side Buttons

The two side buttons most mice carry are reported as SideButton::Back and SideButton::Forward, named by what the system treats each as meaning rather than by its position on the mouse:

PlatformBackForward
Win32XBUTTON1XBUTTON2
LinuxBTN_SIDE, or BTN_BACK on the few mice that report itBTN_EXTRA, or BTN_FORWARD

A side button acts when it is pressed, and a second press within the double-click time counts as one more press. On Win32 the window handles every side button message itself, so the system raises no WM_APPCOMMAND for the same press.

The form passes the press to the control under the pointer as a SideClickEvent that carries the button, and propagates it up the parents until one stops it. A control handles it with an OnSideClick handler, or, when it handles the event for everything inside it, by overriding nestedSideClick:

// Whatever the pointer stands on inside the browser, a side button is its Back or Forward.
void BrowserControl::nestedSideClick(SideClickEvent& event)
{
    Panel::nestedSideClick(event);   // emits; a handler may stop it
    if (event.propagationStopped())
        return;

    event.stopPropagation();
    const std::ptrdiff_t offset = event.button == SideButton::Back ? -1 : 1;
    travel(offset, historyButton(offset));
}

Reaching the Platform From Below

Some of the framework's own services are below the context in the module graph - the clipboard in Transfer, the timer hooks in System - and cannot import the module that declares Platform, because Context imports them. These services still need the platform: the clipboard needs a listener window on Win32 and the display on Wayland, and a UiTimer needs the timer manager. Two seams provide that access, and which one applies depends on whether the service has an object in hand.

The Empty Name and What Stands Behind It

IPlatformServices, declared in ClaFi.Core.System.UiTypes, is a class with a virtual destructor and no other members. It is the name by which a service below the context can refer to the platform, and a service that is handed the platform holds it under this name:

export class Clipboard
{
public:
    explicit Clipboard(IPlatformServices&);
    ...
private:
    IPlatformServices& m_platform;
};

Each platform layer declares its own interface behind the name, in its own module, and the platform built for the display server derives from it:

PlatformInterfaceDeclared inWhat it offers
Win32IMessageWindowFactoryClaFi.Platform.Windows.Window createMessageWindow() - a MessageWindow made from the windows manager, for a service that needs an HWND to listen on.
WaylandIDisplayAccessClaFi.Platform.Wayland.Display display() - the DisplayManager, for the data device, the selection and the change handler.

The service's platform half - the unit compiled for that platform alone - casts the name to the interface that platform implements:

// Windows.Transfer.cpp
IMessageWindowFactory& platform = static_cast<IMessageWindowFactory&>(owner.m_platform);
listener = platform.createMessageWindow();

// Wayland.Transfer.cpp
return static_cast<IDisplayAccess&>(owner.m_platform).display();

The cast is valid because a build has one platform: the object behind an IPlatformServices& in a Windows build is a Win32Platform, which derives from IMessageWindowFactory, and there is no other. The cast also keeps the neutral name empty. IPlatformServices declares nothing that only one platform can implement, so neither platform has to implement a member it does not support - Wayland has no message window, and Win32 has no display object - and the neutral module carries no method that half the builds would stub.

Platform itself does not derive from IPlatformServices; the derived platform does, beside Platform. That keeps the conversion from either platform to the name unambiguous, and keeps Context from having to name the seam.

The Standing Pointer

A hook has no object in hand. PlatformTimer::start and stop are free functions that a UiTimer calls; a DirWatch's platform half is constructed with nothing but the watch; a Platform static is a static. These reach the platform's object through a pointer that the object sets when it is constructed and clears when it is destroyed:

export class TimerManager
{
public:
    [[nodiscard]] static TimerManager* standing() { return s_standing; }
    ...
private:
    inline static TimerManager* s_standing{ nullptr };
};

// the hook
void start(UiTimer* timer, MilliSeconds delay)
{
    TimerManager* manager = TimerManager::standing();
    if (manager == nullptr)
        unreachable("PlatformTimer: no timer manager stands - a UiTimer outlives the platform");
    ...
}
PointerSet byRead by
TimerManager::standing() (Win32 and Linux)The platform's timer managerPlatformTimer::start and stop, the two hooks ClaFi.Core.System.Timer declares and each platform defines.
DirWatchManager::standing() (Linux)The platform's watch managerDirWatch::Impl, the Linux half of a directory watch.
DisplayManager::standing() (Wayland)The platform's display The Platform statics that need the display server: the cursor, the modifiers, the application id, the session.

This is not a singleton. The object is a platform member with a declared place and a declared lifetime; the pointer does not own it, and the pointer is null exactly while the platform holds no such object. A singleton built on first use would respond to a hook called after the platform was destroyed by silently constructing a new manager at process exit. A standing pointer calls unreachable for that hook, because the platform is constructed before anything that owns a timer or a watch and destroyed after it - see First Up, Last Down - and a hook that finds no pointer standing has found a broken order.

Do:

  • Hand the platform's object to whatever you build from it - a window its manager, a buffer its wl_shm - and hold it as a reference member.
  • Use the empty name and a cast when the caller is a service below the context that is handed the platform once.
  • Use a standing pointer only for a hook with no object in hand, and call unreachable when none stands.

Don't:

  • Don't add a method to IPlatformServices. A method there is one every platform must implement, and the name exists to be empty.
  • Don't write a static X& instance() or a function-local static holding framework state. It has no place in the order and is destroyed at process exit, after everything that would have released it.
  • Don't handle a missing standing pointer by doing nothing. Doing nothing leaves the broken order undetected.

The Platform's Own Objects

Each platform layer builds the following objects for the platform that owns them, and each object carries a small set of rules.

On Win32

WindowsManager is the root of the Windows layer. Its constructor sets the process DPI awareness, opens the OLE apartment that the clipboard requires, and registers the four window classes; its destructor closes the apartment, posts the quit message and unregisters the classes. Every window is handed the manager by whoever creates it - the platform to a FormWindow, the platform to the timer's and the clipboard's message windows - and the manager has no static accessor. The one static state it keeps is the desktop's color mode as last read, which a broadcast is compared against.

MessageWindow is a message-only HWND built on WindowBase alone, with no frame, placement, or alpha. Its holder registers itself as the window's IMessageSink and receives every message the window receives, as a Window subclass would; whatever the sink leaves unhandled goes to the system's default. IMessageSink is also the interface the manager's window procedure delivers to for every window it creates, using the pointer in the window's user data, for a Window and a MessageWindow alike.

TimerManager owns a MessageWindow and is its sink for WM_TIMER. It publishes standing() for the two hooks.

On Wayland

DisplayManager is the connection, the bound globals and the event loop. Its constructor connects and throws where it cannot; waitForEvent sleeps on the connection's descriptor, every registered poll source and the appearance bus, and dispatchPending delivers each arrived event to every sink. It publishes standing() for the Platform statics. Apart from the statics that use that accessor, no code reaches the display object by name: windows are handed it, and the clipboard casts to IDisplayAccess.

PollSource is a descriptor's place in the loop, held for as long as the object exists: addPollSource in its constructor, removePollSource in its destructor, with the call to make when the descriptor is readable. The platform declares one per manager, after the display and the manager it polls for.

Linux::TimerManager is a thread that waits out the delays and an eventfd it raises; Linux::DirWatchManager is one inotify descriptor. Both are declared in Platform/Linux because they belong to the operating system rather than the display server. Both publish standing(), and neither references the loop that polls it.

The Clipboard's Two Halves

Transfer::Clipboard is the worked example of a service that is one object with a neutral half and a platform half. The class's own members, declared in ClaFi.Core.Transfer.Clipboard, hold the package this process provides, the held reader, the change dispatcher, and the generation. The platform half is NativeClipboard: a struct the interface declares without a body and each platform's implementation unit of the same module defines, held through a unique_ptr so the interface names no platform type.

Teardown

Construction order is straightforward: the framework's own objects are constructed by whoever owns them, in the order the owner declares. Destruction is harder, because objects being destroyed still reach for the platform, and the platform must still exist then.

What Stays Static, and Why

The rule is that no static holds anything that must be released in an order. A timer, a handle, a thread, a protocol object, or a listener on something else each has an owner with a declared place. The statics that remain hold none of those:

Adding a Platform Service

Adding a platform service means answering five questions, in this order:

  1. Who owns it? A service the platform layer creates from the operating system - a window, a descriptor, an apartment - belongs to the platform. A service the application runs for itself - the animations - belongs to AppContext. No service belongs to a namespace.
  2. Where in the list? After everything it is made from, before everything that is made from it. On Wayland, a descriptor the loop must poll gets a PollSource declared after both the display and the service.
  3. Who reaches it, and from where? Code above the context: give the context an accessor, as clipboard() and animator(). A service below the context that is handed the platform once: add a method to the platform layer's IPlatformServices derivative - IMessageWindowFactory or IDisplayAccess - not to the neutral name. A hook with no object in hand: a standing() pointer on the service, set and cleared by the service, unreachable when null.
  4. Where do the bodies go? A class member is defined in the module that declared its class, so a platform-neutral interface with platform bodies gets one implementation unit per platform of the same module - Windows.Transfer.cpp and Wayland.Transfer.cpp are both module ClaFi.Core.Transfer.Clipboard;. Its platform state is placed behind a struct the interface declares and the platform unit defines, held through a unique_ptr.
  5. What does it do on the way out? A service acts on the way out in its destructor. If it must act while a later platform member still exists, the order is wrong; move it.
