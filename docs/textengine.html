Working with Text in Controls

Text layout, shaping and line breaking

All manuals

Introduction

A control keeps its text as a ControlText, and the TextEngine lays it out: it shapes the text, measures it for the layout pass, and draws it in the paint. Applications use the text through properties that state it and its format, through the calls that read and write it, through events raised around layout, and through anchors that place it inside the control's box. The engine caches the layouts it builds.

The runs, styles, colors, paragraphs and links of a Text are written as the Writing ClaFi Text manual describes.

Module imports: ClaFi.Core.TextEngine for the engine that draws and measures, ClaFi.Core.TextEngine.Layout for TextLayout, and ClaFi.Core.Foundation for the controls and WithTextLayout.

Writing it later

text() returns a live ControlText: a Text that carries a stamp, and every write advances the stamp. A layout or a measurement stores the stamp it was built from, so a comparison of two numbers distinguishes an unchanged text from a new one without reading either. A write does not change a pixel or a size by itself; the caller requests the pass the change requires.

// A text of another size: the form lays out again.
m_status.text() = std::move(status);
m_status.invalidateFormAlign();

// A box whose size is stated: a repaint is the whole of what a new reading costs.
m_readout.text() = std::move(reading);
m_readout.invalidate();
Write through text(), never through a Text& taken from it. A ControlText used as a Text is a value, and a write through that reference does not advance the stamp. A control that identifies its text by the stamp, one that holds its own layout, continues to draw the old text.

Copying and Moving Text

Values and ranges

A Text is a value. Assigning one copies or moves it together with its runs and its style sheet, so a text built for a control is moved in rather than copied, and a text read out of a control is an independent copy.

m_title.text() = Text{ StyledText{ TextStyles::Heading, name } };   // moved in
Text kept = m_title.text();                                               // a copy

selectedText(range) returns a range of a text as a text of its own: the runs of the range, each in the style it had, and the looks of the paragraphs starting in it, its start and its end included, so copied whole paragraphs render as they appear. replaceText(range, text) writes a text into another over a range. The edit history uses both through restorableText and restoreText: a step keeps the text it removed, and an undo restores it exactly, every run in the style and every paragraph in the look it had.

Inserted words take the style of the position where they go. The inserted text is resolved under that style: any field the inserted text states itself takes precedence, and the style supplies the fields it leaves unstated.

  • When a range is replaced, the inserted text takes the style, link and anchor of the first character replaced.
  • At a caret, the inserted text takes the style and anchor of the character before it.
  • At the start of a paragraph, the inserted text takes the style and anchor of the character after it.
  • At a caret inside a link, the inserted text takes the link, because the characters on both sides have it.

A paragraph keeps its look through every edit made inside it. A line end typed inside a paragraph splits it, and both halves keep the look. A paragraph joined to the one above it takes the look of that paragraph, and the first line of inserted text joins the paragraph it is inserted into in the same way. A paragraph that an edit empties takes the first look of the inserted text, so a text pasted into an empty box, or over every word of a paragraph, starts in the look it was copied in.

The clipboard

A TextBox copies its selection in up to three formats, and the clipboard offers plain text converted from the first, so an application that does not use ClaFi can paste the characters:

FormatHolds
ClaFiTextThe selected text over the framework's sheet: each style it is set in beyond the framework's is stored as a style in the text itself, so the copy refers to no style in the sheet it was copied from.
ClaFiStyleSheetThose styles as a sheet, with the style the box's format names where it is beyond the framework's too. Left out where there are none.
ClaFiTextFormatThe box's TextFormat. Left out where the box has none.

Transfer::addText(source, text, format) places those formats on a source, and Transfer::takeText(offer, sheet) reads the text back over the given sheet, or over the application's sheet when none is given: a style whose name the sheet holds is taken from the sheet, and one the sheet lacks is stored as a style in the text, so the text draws as it was copied. A paste tries ClaFiText first and plain text after it; this order alone determines whether formatting survives a paste.

The format is for a preview. A clipboard viewer, WhatsClip among them, draws the copied text with the copied format, as it was drawn where it was copied. A paste ignores it: the box pasted into keeps its own format, so a range copied out of a CodeBox pastes in whatever style the destination box lays its text out in.

Text Events

A control's text is its text(), written by whoever owns the control when the content changes - a reading on its tick, a count as it moves. Every measurement and every paint lays that text out and raises AdjustTextEvent first, where the control, its host and the handlers add material around the text: a mark, a key at the end of a menu line, a parent's text, an answer that differs by phase. The text remains the owner's; the event adjusts what is laid out.

A tooltip is a caption and a body. The presenter that draws the control states the caption line - the control's name and the key that runs it - and AdjustTooltipEvent fills only the body. The body uses balanced wrapping and keeps explicit line breaks. The overflow window repeats the control's clipped text with its original line breaks.

ButtonBase::showsCaption() reports whether the button lays out its caption. A caption on a visible dropdown strip counts. A hidden caption can supply a caption-only tooltip.

A gather runs in one of two phases, which event.phase() reports: Calculate for a measurement, Paint for what is drawn. A control may be measured from a line it never shows - a reading measures the room its widest value needs and paints the value it holds - and a text supplied only in the paint takes no room:

OnEvent{ [](AdjustTextEvent& event) {
    // Measured as nothing, so the tabs beside the title keep the room.
    if (event.phase() == EventPhase::Paint)
        event.text << event.control().appContext().appName();
} }

The gather names a control's own text rather than copying it, so a text that no handler modifies costs only a pointer. A handler that writes adds to the text, and the result is then built. Values computed inside the handler are built at every measure and every paint, so a value that changes independently is written into text() when it changes, and the handlers compose only what the moment of the call requires.

Text Format

A TextFormat defines what a control's text is laid out over: a style name, an ink and a paragraph look. It contains no characters. The engine applies it beneath the text's own styles, and it never becomes part of the text.

// Built like a Text: the stream, or the same sequence as one expression.
TextFormat format{ TextAlign::Center, InkGrade::Muted };
format << TextStyles::SubBody;

What it holds

WrittenHolds
A style name - TextStyles::Code, L"Readout"The style, found where the text is laid out: among the text's own styles and in its sheet, each time the text is laid out.
Ink, InkGrade, InkColor, ColorThe ink the text runs in, spelled as ColoredText spells it.
TextAlign, TextIndent{ f }, TextLineSpacing{ f }The paragraph look, for every paragraph of the text.
TextFormatWhat the other states, each field over this one's.

A size or a family comes in a style. An application states one in its sheet and the format names it:

sheet.set(TextStyle{
    .name = L"Readout",
    .base = sheet.find(TextStyles::Body),
    .fontSize = 11.0f,
});
TextFormat{ L"Readout" };

Values only. A character, a link or an anchor is rejected at compile time, and so is a value that merely converts to one of those types, so a wchar_t is never accepted as a Color.

One of each kind. A value replaces the value the format already holds of its kind, and another format replaces every field it states. Two formats with equal fields compare equal and share one layout in the cache, however they were built.

TextFormat format{ TextAlign::Center, TextStyles::Code };
format << TextFormat{ InkColor::Red, TextAlign::Left };
// Left, red, in Code.

Under the text

The text's own styles take precedence over the format. A field is resolved from the first source that states it: the run's style and its bases, then the format's style and its bases. A face, size, weight or slant that neither states comes from the text's Body, and an ink comes from the text ink. A link's ink sits between the run's ink and the format's. A paragraph's own look overrides the format's in the same way, and where neither states a field the paragraph is left-aligned, unindented and singly spaced.

A style name that the text cannot resolve anywhere is reported with UnknownStyleEvent, as a wrapper's is, and the text is laid out as it would be without it.

A format is how a control shows its text, kept separate from what the text contains. A selection, the edit history and a document see the text alone: a range copied out of a centered box pastes uncentered. A copy stores the box's format beside the text so that a preview can draw it in - see The clipboard. A control with a format and no text is blank.

On a control

Every control built on RichControl takes a TextFormat property and returns it from textFormat() - or no format, while the property is empty. Several formats in one argument list compose kind by kind, and a later one overrides an earlier one; setTextFormat replaces the format as a whole. Stating a format invalidates nothing; the caller requests the pass.

A class states its format ahead of the arguments it forwards, as it states any other property. Along a chain of constructors the caller's value takes precedence for every kind it states, then the most derived class's value, then each base in turn. A CodeBox is laid out in the monospace style this way, and the text passed to it states no style of its own:

TextBox{ params, WordWrap::No, TextFormat{ TextStyles::Code }, std::forward<Args>(args)... }
Never call setTextFormat in a constructor body. The body runs after the caller's properties are bound, so the call replaces them.

The format applies to everything that lays the control's text out: the paint and the measurement, a TextBox's placeholder, the tooltip that repeats the control's clipped text (OverTextAnswer::format), and an in-place editor, which lays out its own text using the covered control's format (EditTarget::textFormat). A grid column states one format for all of its cells - see the Grid manual.

Text Anchors

A control lays its text out in a box, and two anchors determine where the text sits inside that box.

PropertyValuesDefault
VerticalTextAnchorTop, Center, BottomTop
HorizontalTextAnchorNone, Left, Center, RightNone

VerticalTextAnchor positions the text block in the box by its measured height.

HorizontalTextAnchor::None creates no block. Each line is placed across the whole width of the box by its paragraph's TextAlign, and nothing moves it afterward; this suits a page, a grid cell and any text whose lines align to the edges of its box. Left, Center and Right create one: the text is measured as a block as wide as its widest line, each line is aligned inside that block, and the anchor moves the block as a whole. A wrapped text's block is never wider than the width it was broken at.

Drawing and Measuring

The engine builds the layout. A control passes it a text, a rectangle, the colors it resolved, and the position of the text block inside that rectangle:

DrawTextResult drawText(ControlPaintContext&, const FloatRect&, const Text&,
    TextAnchor, const EditProps* = nullptr, bool wrap = true,
    const TextFormat* = nullptr);

ScaledSize measureText(const FormContext&, const Text&,
    MaxSize = { k_maxFloat, k_maxFloat }, bool editable = false, bool wrap = true,
    const TextFormat* = nullptr);

The format is laid out under the text - see Text Format. A null format and an empty format are equivalent, and isTextTrimmed accepts one in the same way.

Colors arrive with the draw. A run names inks, and the paint context passed to the draw resolves them, so the same layout draws correctly through whichever backend owns the form it appears in.

Always pass the anchor. A layout is built at the origin of a box of the given size, and the anchor states where in the bounds that box is placed. A call that omits it draws against a box the text does not occupy. The position each anchor produces is described in Text Anchors.

With CLAFI_TEXT_MOVING set to 1 in Source/Y-Core/System/Switches.h, drawText and TextLayout::draw take a TextRenderMode after the EditProps, and the backends rasterize each run in the requested mode. The switch is 0, and every run is drawn as Static. The mode describes movement, not quality:

ModeFor
StaticText that cannot move. It gets every setting that makes a glyph crisp, because its position never changes.
MovableText that can move, while it is not moving. It gives up crispness permanently rather than at the moment movement starts: every setting that improves crispness ties the raster to a sub-pixel position, so switching the setting around a movement makes the text visibly change at both ends, at rest.
MovingWhile the position is actually changing: outlines filled as geometry instead of a glyph rasterized afresh each frame. This is the expensive mode, so a control that can move but is not moving does not use it.

Passing an EditProps makes the layout editable; editability is a property of the text, not a convenience. An editable text keeps the empty paragraph that a trailing newline opens, because the caret must be able to sit on it. Measured as not editable, that row is missing from the size the control receives.

Some positions in a text are returned without a layout - nextWord, prevWord, wordAt, paragraphAt. A caret position is measured on a TextLayout by whoever holds one, because an edited text is a different text on every key, and routing that through the shared cache would store a copy per press. A paragraph range includes the newline that ends it: a selection that excludes that newline cuts the text and leaves an empty row where the newline was.

A text box holds the layout it draws from instead of taking one from the cache. Its paint, its caret and every position it measures run on that one layout, so a caret is never read off one build and drawn on another.

Line Wrap Modes

TextLayout::setWrapMode controls automatic wrapping. LineWrapMode::None lays out each paragraph on one line. Normal, the default, fills each line in order. Balanced tries narrower widths when an automatically wrapped paragraph ends in a short line. It keeps a narrower layout when it gives more even lines at the same line count.

Each explicit newline ends a paragraph. The optional firstBalancedPosition argument applies balancing to paragraphs that start at or after that offset in Text::plainText(). Justified paragraphs and paragraphs with tabs or flex spaces use normal wrapping. Calling setWrap(true) selects Normal and setWrap(false) selects None.

A control that holds its own layout

When a control needs one

WithTextLayout<HostClass> gives a control a TextLayout of its own to shape in, instead of drawing through the engine's cache. It is written in the base list and nowhere else:

class TextBox : public WithTextLayout<Label>

// A label that rewrites its words needs nothing of its own:
using CaretReadout = WithTextLayout<Label>;
Deriving from the base is the declaration. A control whose text changes often derives from it. A control whose text is written once and never changes does not. No other setting has to match it.

The cache is addressed by what a text contains, so a hundred buttons with the same word share a single shaping. It is also why a text rewritten every frame misses on every paint: the value under a slider's thumb, a frame rate, a caret position in the corner of a scroll box. Each new value takes a fresh entry and evicts a layout that was shared, so a drag of a few seconds empties the cache and forces every label on the form to be shaped again.

A control with its own layout shapes its text in place: there is no hash, no comparison against another control's text, and nothing to evict. Editing is the second reason: an edited text is a different text on every key, and the paint and the caret have to read one build.

The two seams

Two virtuals on Control determine which layout provides an answer, and they are a pair:

virtual DrawTextResult drawText(PaintEvent&, const FloatRect& textBounds, const Text&);
virtual ScaledSize measureText(AlignEvent&, ScaledSize maxDimensions, const Text&);

The framework handles everything around them. paintOwnText provides the rect, the gather and the flags the result raises; measureOwnText provides the gather, the rule that a run which does not wrap is measured against no width, and the clamp to the box.

Override both or neither. A control that overrides one measures on one layout and draws on another.

Bringing the layout up to date

Both seams, and every other call that queries the layout, go through one function, which keeps a position from being read off one build and drawn on another:

TextLayout& syncedLayout(const FormContext&, const FloatRect& textBounds) const;
TextLayout& syncedLayout(const FormContext&, const FloatRect& textBounds, const Text&) const;

virtual void takeText() const;

The one-argument overload gathers a text itself, as a paint does. A second gather of the same text costs no more than the first: a gather names a control's own text rather than copying it, so the layout identifies an answer that is that object by its stamp, and an answer composed around it - a parent's text, a mark - is stored in a copy beside the text and compared with the next one. The text remains what its owner wrote, and the layout draws whichever of the two the last gather produced. In either case an unchanged text rebuilds nothing, and a control measured four times in one pass shapes once.

Only the size of the rect is used. Its position belongs to the caller and the anchor, so a control moved sideways under a viewport does not rebuild for every pixel of movement.

A layout held here is outside the cache, so it handles invalidateLayouts() itself: it compares layoutGeneration() against the number it was built at, and invalidates when the two differ.

The control's format is passed to the layout the same way, on every call. TextLayout::setFormat stores a copy and compares it with the format passed next time, so an unchanged format invalidates nothing, and a measurement from an earlier call is returned again only while the format matches the one it was made with.

takeText states the whole of a text that the layout has not been told about; this is the call for a text rewritten from nothing. A host that tracks what changed overrides it and reports the change instead - see Editing a layout in place.

Positions on a held layout

Whoever holds a layout queries it for positions. The word-level functions above need no layout; these do, because the results are about lines, and lines exist only once a text has been broken to a width.

CallAnswers
caretPos(FloatPoint)The CaretHit a point names: an insertion position, and the affinity that says which of two rows a position on a break belongs to.
getCaretRect(CaretHit)Where that position stands.
posOnNextRow(CaretHit, ScrollDirection, targetX)The position one row up or down. targetX is the column a run of arrow keys is holding, so a short row passed through does not pull the caret in with it.
rowStart(CaretHit), rowEnd(CaretHit)The two ends of the row the position stands on - where Home and End go.
lineColumnAt(size_t)Which line the position is on and how far into it.
struct TextLineColumn { size_t line{ 1 }; size_t column{ 1 }; };
A row is produced by the line breaker; a line is the text between newlines. A row changes with the width the text was broken at, and a paragraph broken across five rows has one line number, with the column counted across the whole paragraph. Both are counted from one.

lineColumnAt is a binary search over the paragraphs and does not read the text, so a status readout can call it on every key press of a fifty-thousand-line document. The row functions visit the paragraphs, which is the cost of a result that depends on where the lines were broken.

All of these are in the layout's own coordinates - the box is built at the origin. A control applies anchoredOrigin in both directions: subtracting it from a point passed in, adding it to a rect returned.

Folding paragraphs

TextLayout::setHiddenParagraphs takes sorted, non-overlapping ranges of zero-based paragraph indices. The first paragraph stays visible. An empty list restores all paragraphs. Hidden paragraphs take no vertical space. Text positions and line numbers still refer to the full text. A caret rectangle for a hidden position is returned at the end of the preceding visible paragraph. Update the ranges when an edit changes their indices. paragraphVisibilityRevision() changes when the supplied ranges change, so a caller can include it in a measurement cache key.

CodeBox uses the language's block boundaries to show gutter chevrons. A collapsed block marks its opening line with an ellipsis and hides the lines through its closer. Searches and copies still use the full source. The gutter's context menu offers Expand all, Collapse all, and Collapse others. Collapse others keeps open the blocks containing the clicked line.

Editing a layout in place

A layout is normally given a whole text. A caller that tracks the change can report it instead, and then a paragraph the edit did not reach keeps the shaping it already has:

struct TextEdit { TextRange replaced; size_t insertedLength; };

[[nodiscard]] bool applyTextEdit(const Text&, TextEdit);
[[nodiscard]] TextEdit mergedEdits(TextEdit first, TextEdit second);

The edit is stated in the coordinates of the text before it. The layout finds the paragraphs the edit reaches, re-shapes those, and moves the rest: their characters begin later or earlier, and their lines sit lower or higher. Typing a newline, deleting one and pasting a thousand lines are all the same operation; the number of paragraphs the slice became is read from the rebuilt text rather than worked out from the edit.

An edit can fail, and the return value reports it. applyTextEdit returns false when the layout has nothing shaped yet, or when the edit does not fit the text it is given. A caller that receives false states the whole text with setText; the layout is already invalidated for it.

One record carries one edit, and key repeat runs faster than the paint loop, so several edits can reach the text before anything queries the layout. mergedEdits folds a second edit into an existing record and returns the hull of the two. A hull can name text that neither edit touched, which may re-shape a paragraph unnecessarily, or cause a refusal; it never produces a wrong answer.

A caller must also establish that the record describes this text. An edit and a text belong together only when their lengths agree: the text the layout holds, plus what the edit inserted, less what it replaced. A control whose text arrives from its parent edits its own text, and the two are not the same text.

Links in a TextBox

A link and an anchor are written as the Writing ClaFi Text manual describes, and what a link does depends on the control that holds the text: a TextBox follows it, and a label draws it and nothing more. The control underlines the link under the pointer when a click there would follow it.

Following a link in a TextBox

BoxFollows a link onA plain click on a link
Read-onlyA clickFollows it.
One the user types intoCtrl+clickPlaces the caret, as it does anywhere else in the text.

The same rule controls when a link is underlined and when the hand pointer is shown, so the element under the pointer always indicates what a click there will do. A press that ends in a selection was a drag, and it follows nothing.

A followed link is resolved in this order:

  1. When the box's own text holds the #name, the box goes to that anchor. The anchor's text is selected, and its line is brought to the top of the view, as a browser does for a fragment. No event is raised.
  2. Any other target raises OnLinkClick with that target. A handler that acts on the target stops the event.
  3. A target that no handler stopped is opened through the shell when it starts with http:, https: or mailto:, whatever its letter case. Every other target goes nowhere.
box.onLinkClick([](LinkClickEvent& event) {
    if (!event.target.starts_with(L"clafi:"))
        return;
    openPage(event.target.substr(6));
    event.stopPropagation();
    });

LinkClickEvent carries target, as the text states it, and stamp, the press that followed the link. A #name that the box's text does not hold is raised like any other target, which is how a link reaches an anchor on another page: the handler opens that page and calls goToAnchor on its box.

The shell opens three schemes only. A text read from a file or from the clipboard can hold any target, and the shell runs any program it is handed. A file: link, a path or a scheme of the application's own does nothing until a handler acts on it.

Back and forward

// false, and nothing moves, where the text holds no such anchor
bool goToAnchor(std::wstring_view name);
void goBack();
void goForward();
bool canGoBack() const;
bool canGoForward() const;

Every jump is remembered. Before going to an anchor, the box records its current position - the selection, and the position the view showed at its top - and Alt+Left goes back to it while Alt+Right goes forward again, as a browser's history does. goToAnchor records a position whether a link or the application called it. With nothing to go back or forward to, the key is left unhandled and passes to the control above the box.

An edit made through the box moves every remembered position with the text, so going back after typing returns to where the user was. An undo or a redo clears the history. A text written by the host leaves the history intact, and a position past the end of that text is clamped to its end when it is restored.

Link tooltips

Every link has a tooltip, whether a click would follow it or not: the underline indicates that a click would follow it, and the tooltip shows where the link goes, which is as useful in a box the user types into as in one the user reads. The tooltip is placed over the line the pointer is on, starting where the link starts on that line, so it covers neither the link nor the words around it. Where the screen has no room above the line, it is placed under it. While the pointer is on a link, its tooltip replaces the box's own.

When no handler writes a tooltip, the box supplies it:

TargetTooltip
#name, held by the box's textThe paragraph that contains the anchor, with its formatting - in the Ledger, the clue that a reference names. A paragraph longer than six lines is cut at the end of the sixth line and ends in an ellipsis, in the styles still open at that point.
Any other targetThe target as the text states it.

In a box the user types into, the tooltip also shows a muted line: Ctrl+click to follow. A plain click there places the caret, and no other element on screen indicates that the link can be followed.

OnGetLinkTooltip is raised first. Its event carries target, range - the text the link covers - and tooltip, the tooltip itself with its placement and anchor already set. Whatever a handler writes into tooltip.text becomes the entire tooltip, and the box then writes nothing.

box.onGetLinkTooltip([](GetLinkTooltipEvent& event) {
    if (event.target.starts_with(L"clafi:"))
        event.tooltip.text << L"Opens the " << event.target.substr(6) << L" page";
    });
A tooltip breaks its lines at 480 design pixels, and its window is sized to the widest line in it, so a short tooltip stays short and a long one wraps instead of extending to the edge of the screen. This applies to every tooltip except one over a control's own text, which repeats the lines that control broke. A preview is cut at six lines of that width.

Links on a held layout

A control that draws links of its own - one that holds its own layout - queries the layout for the link under a point and sets which link is underlined:

[[nodiscard]] std::optional<LinkHit> linkAt(FloatPoint);
void setHoveredLink(TextRange);     // an empty range underlines nothing
TextRange hoveredLink() const;

struct LinkHit { LinkSpan link; size_t pos; };   // the link, and the character under the point

linkAt takes a point in the layout's own coordinates, the coordinates that caretPos takes. A hit test returns the nearest character even past the end of a line, so the point is confined to the box that contains that character's glyph: past the end of a line, between two lines or below the text, there is no link. pos is the character under the point, which identifies the line of a wrapped link that the pointer is on.

The hovered link is read at draw time, as colors are: stating one shapes nothing, and the caller repaints. A new text clears it, since the range was stated in the text where it was found.

LinkSpan is TextSpan<std::wstring_view> - the range a link covers and its target - and BakedText::links() returns every link in text order. The target is a view into the text the spans were baked from, and remains valid while that text is unchanged.

Do and Don't

Do

  • Build a Text per paint. An identical text hits the layout cache, so rebuilding costs a hash and a compare.
  • Write a control's text through text() and request the pass the change needs.
  • Pass the anchor that matches how the control positions its text.
  • Leave the horizontal anchor at None for text whose lines align to the edges of their box.
  • State what every text of a control shares as its TextFormat, ahead of the arguments a constructor forwards, rather than writing it into each text.
  • Handle your own link targets in OnLinkClick and stop the event. For any target the handler does not stop, the box opens only http, https and mailto.

Don't

  • Don't hold a Text to avoid rebuilding it unless it is expensive to assemble. The layout cache is part of the engine, not of the control.
  • Don't write through a Text& taken from text(). The stamp stays where it was.
  • Don't measure editable text as static and then draw it editable. The two produce different heights.
  • Don't call setTextFormat in a constructor body. It replaces what the caller passed.
  • Don't put a text that changes while the user watches through the cache. A control whose text changes often derives from WithTextLayout and shapes it in place.

How It Works

Runs to spans

BakedText::rebuild iterates over the runs once and resolves each field of each run from the first source that states it - the run's style and its bases, then the format's style and its bases, then the text's Body for a font field and the text ink for an ink. Equal neighbors merge, and the output is absolute ranges: ColorSpan, WeightSpan, StyleSpan, SizeSpan, FamilySpan, ScriptSpan, a ParagraphStyle per paragraph, a LinkSpan for every link, and a BakedInlineObject for every inline object. The native layout is fed that form.

A color span holds ColorDef, which is std::variant<Ink, Color> - the name of a color rather than a color. Colors are deliberately absent from the input of a build: they are applied to the native layout when it is drawn, so a theme change redraws the same shaping rather than shaping it again. Alignment is absent for the same reason: where finished lines sit inside their box is set on a built layout, not derived during shaping.

The base font is the format's style over the text's Body, resolved once per bake. A text holding nothing is drawn in it and its caret is measured in it, and a layout uses it for every field that a paragraph's spans leave unstated.

The layout cache

The engine keys its layouts on a text rather than on a box: the text's hash, the hash of the format it is laid out over, the scale factor, whether it is editable, and - for a text with a flex space - the event phase. A flex space is the one item laid out differently for a measurement and for a paint, filling the box it is drawn in and contributing nothing to a size. Floats are keyed by their bits, because this is an identity question and not a numeric one.

From 512 layouts on, the engine sweeps: it keeps the layouts that the current pass and the previous pass requested. Past 4096 it keeps the most recently used half.

A key names a bucket, and the bucket holds one layout per width at which the text has been broken. Lines broken at one width are no wider than the widest of them, and every width between the two breaks them the same way: no line has to split, each already fits, and no two can join, because the breaker refused the next word at the wider of the two. The engine queries a layout for the width being requested, and the first that accepts it supplies the layout. One build can therefore serve both passes: a control is sized to what it measured, so the paint queries a width inside the interval of the build that the measurement just made. A width outside every interval takes a layout of its own, up to four to a text, and the least recently used one is evicted.

The box a layout occupies is not the width its lines were broken at, and moving lines into another width requires no shaping. A paragraph that came out as one line is placed by an offset that the layout applies as it is drawn or hit; one of several lines is aligned by its native layout once, in the width it was broken at, and then moved as a whole. A wrapped text is never placed wider than it was broken at nor narrower than its widest line, so every line of it moves by the same amount. Justified lines are stretched to the width they occupy, and only those lines receive a new width.

The height is not part of a layout's key. It determines which line the text is cut off at and which lines fade, and those are read from the finished lines, so a box of another height keeps the shaping and recomputes the fit.

A hash locates an entry but does not prove it is the right one - two texts landing on one would draw the wrong words - so a hit is confirmed by comparing the Text itself and its format against the copy the layout keeps. The cache owns the text's copy, because every caller's text is a temporary built for one paint, while the layout keeps a pointer to the one it was given.

Text::hash covers the whole Text, including the inks of its runs. A color is no part of a build, but it is part of what makes one Text different from another Text, so two runs naming different inks hold separate cache entries rather than sharing a key and evicting one another on every alternation. For anything that changes what a build would produce without being part of the key - the font table above all - invalidateLayouts() clears the cache and advances layoutGeneration(), and a layout held outside the cache compares that number against the one it was built at. An edit to any style sheet advances it as well.

Paragraphs on cells

A paragraph set in one monospace font is not shaped. Every glyph of such a font is one cell wide, so the x of a column is the column times the cell, a tab advances to the next multiple of four columns, the line is one row of the face's height, and a hit test is a division. The layout applies this rule per paragraph, before building anything: one font over the whole paragraph - a span of family, size, weight or style ending inside the paragraph makes a paragraph in two fonts - no inline object, no script, not justified, and every character either a tab or one the font has a glyph for at exactly the cell advance. A paragraph that qualifies is one row of columns times cell and holds no native layout. Anything else is shaped natively, that paragraph alone: one line of Arabic in a source file costs that line and no other.

The gain is in shaping. A document of source is one pass over its characters instead of a native layout per line, and the layout keeps a paragraph record per line rather than a native object for each: the lines of every paragraph live in one pool on the layout, so a document of a hundred thousand rows allocates space for them once. The pixels are the ones the native layout would draw: DirectWrite's natural measuring mode places a monospace run at column times advance, the tab stops are the same four cells, and the glyphs use the same draw primitive - DrawGlyphRun on Direct2D, the glyph cache and the compositor on the CPU backends. The cell and the line height are the platform's own measurement of the font, the same one from which the tab stops are read.

A paragraph on cells draws one glyph per character. Ligatures are not applied to it. Consolas and DejaVu Sans Mono have no ligatures; Cascadia Code and Fira Code do, and a text set in one of those shows its characters unjoined.

Text that a glyph table alone cannot lay out stays native, and the layout rejects it without querying the font: the controls and the format characters, combining marks, the right-to-left scripts, the scripts that reorder or stack, and anything past the basic plane. A wrapping layout keeps a paragraph on cells while its ink fits the width it breaks at - a line that fits is never broken - and passes one that does not to the native layout. Left, center and right alignment are an offset inside the width the paragraph is placed in, applied as the paragraph is drawn or hit rather than passed to a layout, so a box that moves requires no rebuild.

No API reports which paragraphs are on cells. [code] text, a CodeBox, a HexView line and a label in a monospace family all use this path when they qualify, and a caller reads the same positions and draws the same pixels either way.

The link underline

The layout draws the underline of the hovered link: one segment per line the link reaches, under the glyphs that the line shows, in the color of the segment's first glyph. The underline is placed below the baseline by a share of the space the line has there, in the thin stroke; the font's own underline metrics are not read. It is drawn over the glyphs, so a selection band does not cover it, and it does not fade with the glyphs of a line that the box cuts off.

Where the underline would cross ink, it is cut. The native layout reports where the link's glyphs put ink between the line's top and bottom edges - INativeTextLayout::appendInkAcross, and INativeMonoFont::inkAcross for a paragraph on cells - reading the same glyph coverage that the CPU path draws, a row at a time, and counting a pixel as ink past a fifth covered. Each stretch is widened by the line's thickness on both sides and removed. A piece no longer than the line is thick is not drawn, since it would read as a dot between two descenders. On Direct2D the glyphs of a hovered link are rasterized into the CPU glyph cache for this purpose.

The layout stores nothing: the ink is queried on every paint while a link is hovered, and that is one or two lines of a single link.
