Editors and tooling

Why is the source covered in red squiggles?

The marks come from IntelliSense, not from the compiler.

Why

Visual Studio's C++ IntelliSense does not process C++20 modules, and the support it provides is labeled experimental. It marks correct source red, and no edit to that source removes the marks.

ReSharper C++ reads the modules with no setup. The clangd language server reads them once you configure the CMake build and point your editor at the compile_commands.json that build writes into the build directory.

Why does clang say a member is not yet bound in my constructor?

Clang checks a constructor template without the default member initializers. Build the member where it is declared, and pass it the argument in the constructor body.

Why

A control holds its children as members, each built by its default member initializer, and members are built in the order they are declared. An entry of the constructor's initializer list that reads a member declared above it reads one that is already built, so the code is correct C++.

Clang's -Wuninitialized checks a constructor template as if those initializers were not there, and a control's constructor is a template, because it forwards the properties it is given. So every such read is reported: reference 'm_topBar' is not yet bound to a value when used here for a reference, field 'm_count' is uninitialized when used here for a pointer or a value. A constructor that is not a template is checked with the initializers, and nothing is reported.

The child that needs the argument is built where it is declared, like every other child, and the argument is passed to it in the constructor body: 

class TitledPage : public Panel
{
public:
    template <typename... Args>
    TitledPage(const CreateParams& params, std::wstring_view title, Args&&... args);
private:
    Panel& m_topBar{ createTopBar<Panel>(Padding{ 12.0f, 8.0f }) };
    Label& m_title{ m_topBar.createBody<Label>(VerticalTextAnchor::Center) };
};

template <typename... Args>
TitledPage::TitledPage(const CreateParams& params, std::wstring_view title, Args&&... args)
    :
    Panel{ params, std::forward<Args>(args)... }
{
    m_title.text() << StyledText{ TextStyles::SubTitle, title };
}

Layout and scrolling

Why are scroll bars missing?

State WordWrap::No on the scrolled control.

Why

The symptom is a control inside a ScrollBox that draws its content correctly and is visibly cut off at the edge of the box, with neither bar on screen — including under ScrollBars::Both, which requests both bars.

With Both, both bars are present. A bar whose range has nothing to scroll is disabled (SliderBase::getControlState tests maxPos() > 0), and a disabled bar draws neither its thumb nor its buttons, whatever their own states say. An empty view therefore means the content is no larger than the view. The next question is why the content came out that size.

The body wraps

The usual cause is the body wrapping, and nothing reports it. Control::wordWrap() is !(m_flags2 & cfNoWordWrap) — true for every control by default, including one that holds no text. Control::alignContent then checks it: 

if (wordWrap())
{
    // Measured again against the slot it was granted, and the slot is the viewport.
}
else if (isOnScrollBox())
{
    // A scrolled body keeps the size it measured.
    newDimensions.y = std::max(calculatedContentHeight, newDimensions.y);
}

The rule in "A scrolled body keeps what it measured" applies to the second branch only. A wrapping body never reaches that branch: it is measured again against the slot, so it cannot come out larger than the view. For a control that draws its own content and holds no text, the re-measurement returns {0, 0}, which is discarded rather than taken, so the slot size stands and the body ends up exactly the size of the viewport. max == page, so there is nothing to scroll and both bars are hidden.

The flag is a property of the body, and it can be stated in three places. One is the construction property where the body is made, which is how a stock control such as a TextBox takes it: 

BodyProps{ ReadOnly::Yes, WordWrap::No, Padding{ 12.0f } }

Another is in the constructor of a control that can never wrap, ahead of the forwarded arguments so that Props still takes a stated one — it reads the last match: 

template <typename... Args>
HexView::HexView(const CreateParams& params, Args&&... args)
    :
    Control{
        params,
        // A line is a fixed grid of characters and nothing about it can be broken to a box.
        WordWrap::No,
        std::forward<Args>(args)... }
{
}

The third is setWordWrap(WordWrap::No) on a control that is already built.

Do

  • State it where the body is made, in the properties that build it. This works for any control whose source you are not editing.
  • A control that can never wrap states it in its own constructor instead, so that no caller has to set it. ComboBox and HexView both do.

Don't

  • Assume a control holding no text is unaffected. wordWrap() is true by default for every control, and a control that draws its own content is the case where the wrapping branch measures {0, 0} and the slot size stands.
  • Reach for MinSize to force the body taller. The measured size is already correct; what is missing is the word-wrap flag.
The same flag also controls the width. ScrollBox::adjustChildMetrics uses the viewport as the maximum width of a wrapping body, so such a body is never wider than the view and the horizontal bar has nothing to scroll. Both bars are controlled by the same flag.

ScrollBars::Auto on a box that does not measure itself

The other cause is not fixed by WordWrap::No. Auto is decided in ScrollBox::calculateContent against the box's own maximum size, which lets the measuring pass decide it in one go with no correction afterward. It therefore applies to a box that measures itself: one under a MaxSize, or one that is the whole content of an auto-fitting window. A box sized by whatever contains it has no maximum of its own and never shows an Auto bar. Such a box states the bars it wants instead, with Both, Vertical or Horizontal.

wordWrap is a text property about reflow: it records whether the control's measurement depends on the width it is given. Any control whose measurement does not depend on width has the same problem, not only a control that draws its own content; a container of naturally sized items in a scroll box is another case.

Color and themes

Why doesn't the application follow the desktop's dark mode?

Choose Auto (Follows System) on the Settings page.

Why

The symptom is that the desktop is dark and the application opens light, or that the desktop changes mode and the application keeps the mode it had.

The config states a mode outright

Auto is the default when the config states nothing. A config that states ColorMode=Dark or ColorMode=Light keeps that mode whatever the desktop does: a click on a mode button stores one, and an application can set its own first-run default - the TextEngine showcase states Light. To fix it, set Auto: 

application.themes().setColorMode(ColorModeSetting::Auto);

Windows is asked for its app mode

Windows has two modes: one for Windows itself - the taskbar and the Start menu - and one for applications. Auto follows the second, Choose your default app mode in the color settings. When the app mode is Light, the application opens light even if the taskbar is dark.

A Linux session without a portal

On Wayland the mode comes from the XDG desktop portal, which GNOME, KDE Plasma and most desktops start with the session. A session without a portal, or with a portal whose backend serves no org.freedesktop.appearance, states no preference, and no preference is read as Light. The portal setting can be read with one call: 

busctl --user call org.freedesktop.portal.Desktop /org/freedesktop/portal/desktop \
    org.freedesktop.portal.Settings ReadOne ss org.freedesktop.appearance color-scheme

The call returns v u 1 for dark and v u 2 for light. v u 0 is no preference, and the GNOME portal returns it when its default light theme is in use.

Do

  • Leave the choice to the user. Auto is the default because the desktop setting records the user's choice.
  • State a first-run default only where the application needs a particular mode, and only where configFolderExists() is false.
  • Call ThemesManager::resolvedColorMode() for the mode the application is drawn in.

Don't

  • Write a mode over a loaded config at start. The load restores the user's choice, and a mode written after it undoes the Settings page on every run.
  • Treat the setting as a fixed mode. Under Auto it names none, and a test for ColorModeSetting::Dark is false on a dark desktop.

Text and links

Why doesn't clicking a link open it?

Hold Ctrl while you click.

Why

The symptom is a link in a TextBox that is drawn in the accent color, where a click places the caret there and nothing opens. The pointer stays an I-beam over it and no underline appears.

The box is one the user types into

In a box the user can edit, a plain click places the caret as it does anywhere else in the text, because a link is a word the user may want to change. Ctrl+click follows it, and while Ctrl is held, a link the pointer moves onto is underlined and the pointer becomes a hand. The tooltip over the link states it as well: in an editable box it ends with a muted Ctrl+click to follow.

A box meant for reading follows a link on a plain click. That is a property of the box: 

BodyProps{ text, ReadOnly::Yes, Padding{ 16.0f } }

The press became a drag

A press that selects text between going down and coming up is a drag and follows nothing, even when it starts and ends on the same link. A pointer that moves a few pixels while the button is down can select a character.

The box is disabled

A disabled box takes no input, so it follows nothing, underlines nothing, and shows the arrow over its links.

The underline and the hand appear exactly when a click would follow the link. A link that shows both and still opens nothing has a different cause.

Do

  • Make a box meant for reading ReadOnly::Yes. Its links then follow on a plain click, and its caret and selection still work.

Don't

  • Follow a link on a plain click in a box the user types into. Every click that was meant to place the caret inside a link would open the link instead.

Why does a file: link do nothing?

For a file or folder your application presents, use text << context.fileLink(path);. To interpret a file: URL supplied in a document, handle it in OnLinkClick.

Why

The symptom is a link that is underlined under the pointer, with the pointer shown as a hand, so a click follows it and nothing opens.

How a link is opened

A followed link raises OnLinkClick with its target. If the event continues, the application opens paths it has registered through fileLink and URLs with registered schemes. The built-in URL handlers cover http:, https: and mailto:. A document or the clipboard can supply a file: URL. An application can interpret such a URL in its link handler. 

box.onLinkClick([](LinkClickEvent& event) {
    if (!event.target.starts_with(L"file:"))
        return;
    // Open what the application trusts, and only that.
    openDocument(event.target);
    event.stopPropagation();
    });

A # link to an anchor the box does not hold

A #name that the box's own text holds is followed by the box with no event raised. A name it does not hold is raised to OnLinkClick like any other target; this is how a link reaches an anchor on another page, where the handler opens that page and calls goToAnchor on its box. With no handler, it goes nowhere.

Do

  • Stop the event once a handler has processed the target, so the box does not act on it as well.
  • Check a target before opening it. The text it came from may not belong to the application.

Don't

  • Pass every target to the shell from a handler. That removes the one guard the box applies, for every text that reaches it.
  • Leave the event running after opening an https: link yourself. The box opens it a second time.

What a followed link does is described in the TextEngine manual, under Following a link in a TextBox.

Settings and documents

Why does the build say a type must define serializedFields?

Import the serializer's module where the value is read or written, or re-export it from the module that states the struct's fields.

Why

The symptom is a struct that gains a Color member - or any other type with a ScalarSerializer - and a build that stops in the Dom engine at static assertion failed: 'Type must define k_serializedFields, serializedFields member, or an ADL serializedFields() function.' The serializer exists, and the struct's fields are stated.

The serializer is out of sight

The engine decides whether a type is a scalar by looking for its ScalarSerializer in the file that reads or writes the value. When none is visible there, the type is treated as a struct, and a struct whose fields are not stated stops the build. A serializer is visible to the file when the file imports the serializer's module itself or imports a module that re-exports it. A plain import in a module further up the chain does not make it visible.

The instantiation context in the error names the file the import belongs in - the get<T>(), set() or Dt::Value that reads or writes the struct - and further down, the member type whose serializer is not visible.

The fields module re-exports what its members need

The module that states serializedFields for a struct is the one whose members determine which serializers are needed. Re-exported from that module, they are visible to every file that can see the fields: 

export module MyApp.Swatch;

export import ClaFi.Core.Dom_UiSerializers;

import ClaFi.Core.System.Serialization;
import ClaFi.Core.System.UiTypes;
import ClaFi.StdLib;

export struct Swatch
{
    Color fill{};
    Color stroke{};
};

export constexpr auto serializedFields(const Swatch&)
{
    return std::make_tuple(
        SerializedField{ L"Fill", &Swatch::fill },
        SerializedField{ L"Stroke", &Swatch::stroke }
    );
}

Do

  • Re-export the serializers a struct's members need from the module that states its fields.
  • Import ClaFi.Dom in application code that reads or writes values. It re-exports the standard and the UI serializers.

Don't

  • Import the serializer without export into a module further up the chain. The file that reads or writes the value still does not see it.
  • State fields for a scalar type to silence the error. Wherever its serializer is visible the type is still a scalar, so one type would be written two ways.

Which module holds which serializer is in the Dom manual, under Where a Serializer Must Be Imported.
