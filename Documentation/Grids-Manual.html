ClaFi Grid

Building grids was never that simple

Introduction

The structure you see in that picture — different column levels, visual cell spans and merges, groups — falls out of two hierarchies, a tree of columns and a tree of rows, plus one fact per cell: whether that row fills that column.

You describe all of it — columns, rows, and the contents of every cell — as a single nested declaration:

Grid m_blueprint{ m_grid,
    Columns{ /* the column tree */ },
    Header{}, // The grid header is optional, this line creates one
    Rows{ /* the rows, and the cells in them */ }
};

Applying it builds the grid and, for each row, connects a pair of handlers to that row: one answering which columns the row fills, one supplying the text of its cells. The grid asks the row while it lays out, paints and hit-tests, so there is no second place to keep in sync. The row owns those connections, so nothing outside the grid has to stay alive.

The one idea to carry through this document: a grid is a sparse matrix. Which cells exist is the most important thing about it — it drives layout, painting, merging, hit testing and keyboard navigation. With the Blueprint, a row's cells are exactly the ones you list, and nothing else.

Quick Start

A grid with two columns and two rows. This is the whole thing:

import ClaFi.Controls.Grids;
import ClaFi.Controls.Grids_Dt;

using namespace ClaFi;
using namespace ClaFi::Controls;   // Grids:: and Dt:: from here on

enum class Col { Name, Size };

class FilesPage : public BasePage
{
    Grid& m_grid{ body().add<Grid>() };

    Grid m_blueprint{ m_grid,
        Columns{
            Column{ Tag{ Col::Name }, Text{ L"Name" } },
            Column{ Tag{ Col::Size }, Text{ L"Size" } }
        },
        Header{},
        Rows{
            Row{
                Cell{ Tag{ Col::Name }, [](CellTextArgs& a) { a.text << L"readme.txt"; } },
                Cell{ Tag{ Col::Size }, [](CellTextArgs& a) { a.text << L"1.2 KB"; } }
            },
            Row{
                Cell{ Tag{ Col::Name }, [](CellTextArgs& a) { a.text << L"notes.md"; } },
                Cell{ Tag{ Col::Size }, [](CellTextArgs& a) { a.text << L"640 B"; } }
            }
        }
    };
};
Three namespaces, and you name none of them. The grid's runtime classes live in ClaFi::Controls::Grids — plural, so that Grid stays free as a class name. The blueprint layer is ClaFi::Controls::Grids::Dt. The machinery both of the framework's blueprint layers share — OnEvent, Init, the node bases, the pack routing — lives in ClaFi::Dt, and Grids::Dt re-exports the parts you name directly.

Pull the blueprint layer in once, in the namespace your page lives in, and write every node unqualified after that: 
namespace MyApp
{
    using namespace ::ClaFi;
    using namespace ::ClaFi::Controls;
    using namespace ::ClaFi::Controls::Grids::Dt;
Two names still need qualifying, because they collide with the controls of the same name in Controls::: Grids::Dt::Expander and Grids::Dt::Divider. Everything else is written bare.

Grids_Dt also publishes Grids::Rt::, aliases for the runtime types a blueprint mentions: Rt::Column, Rt::RowBase, Rt::RowContainer. The same classes, spelled so that a blueprint reads visibly differently from the live objects it describes.
Two imports. import ClaFi.Controls.Grids; brings the grid and import ClaFi.Controls.Grids_Dt; brings the declarative layer. The second pulls in ClaFi.Core.Dt for you.

Four things to notice, because they apply everywhere:

  • The Grid applies itself in its constructor, so it has to be declared after the grid it builds into. It keeps nothing afterwards, so it can equally be a local in a constructor body rather than a member.
  • A column is named by its Tag — an ordinary property, forwarded to the column like any other. Any enum or integer works. The values have to be unique among the columns of one grid, and a debug build says so if they are not.
  • A cell names its column with that same Tag — Cell{ Tag{ Col::Name }, ... }.
  • A row has cells only where you give it cells. A row with no cell in Col::Size has no cell there at all — not an empty one.

Text usually comes from your data rather than a literal. Point the cell at a member function and it will be called whenever that cell needs drawing:

void FilesPage::nameCell(CellTextArgs& args) const
{
    args.text << m_files[args.row.tag<size_t>()].name;
}

// ...
Row{ Tag{ index }, Cell{ Tag{ Col::Name }, this, &FilesPage::nameCell } }

Tag is yours to use however you like — here it carries the row's index into the model. The grid never reads it.

Core Concepts

Columns

Columns form a tree. Any column can have sub-columns:

Column{ Tag{ Col::Range }, Text{ L"Range" },
    Column{ Tag{ Col::RangeMode },   Text{ L"Mode" } },
    Column{ Tag{ Col::RangeAmount }, Text{ L"Amount" } }
}

Anything in a Column that is not another Column is a property. The useful ones:

PropertyEffect
Text{ ... }The header label, and the default text of the header cell.
ShowInHeader::Yes / NoWhether the header row draws a cell here. Default Yes.
ColumnWidthMode::FitContentAs wide as its widest cell. The default.
ColumnWidthMode::FixedAs wide as the float you also pass.
ColumnWidthMode::FillTakes a share of the leftover width. With several Fill siblings the float acts as a ratio.
TextAlign::...Alignment for every cell in the column.
const ColorRule*Background tint for the whole column.
Tag{ ... }Names the column, so a cell can refer to it and columnByTag can find it afterwards. Unique within the grid. Reaches the column like any other property.

Rows

Rows appear in the order you declare them. Besides plain Row there are containers that hold other rows:

NodeProduces
Header{}The header row. Draws a cell in every column whose ShowInHeader is Yes, using that column's Text.
Row{ ... }An ordinary row. Can hold text cells and live controls.
Divider{}A thin band between rows, closed by a grid line.
Expander{ Header{...}, rows... }A collapsible header with rows beneath it.
Group{ Span{...}, rows... }A span row laid over its rows, so its cells span them vertically.
Rows{ ... }Grouping only — adds nesting in your source, not in the grid.

Cells and content

The Text handed to a provider is a stream the grid clears once per query, and providers append to it. Several levels can contribute to one cell — the cell's own provider, then a grid-wide OnGetCellText handler. One that wants to replace what an earlier one wrote calls text.clear() first.

A row's cells are exactly the ones you declare. Four forms:

// The cell exists and is empty. It still draws a border and can be hovered.
Cell{ Tag{ Col::Amount } }

// Text from a lambda.
Cell{ Tag{ Col::Name }, [](CellTextArgs& args) { args.text << L"..."; } }

// Text from a member function - the usual choice.
Cell{ Tag{ Col::Name }, this, &MyPage::nameCell }

// A live control living in the cell.
CellWith<Combobox>{ Tag{ Col::Mode }, /* Combobox constructor arguments */ }

A text provider receives:

struct CellTextArgs
{
    const Rt::RowBase&  row;     // which row - read its Tag to find your data
    const Rt::Column&   column;
    Text&               text;    // write here, appending
};
Not declaring a cell is different from declaring an empty one. A column you skip has no cell in that row: nothing is drawn, and either a neighbouring cell covers the space or it stays blank. A bare Cell{ key } gives you a real, bordered, hoverable cell that happens to be empty. Both are useful; pick deliberately.

Merging

Cells grow to cover their neighbours in two ways. Neither is configured — both follow from which cells you declared.

A column whose cell covers its sub-columns

If a row fills a column but none of that column's sub-columns, the cell spans downward over them. The result is always a plain rectangle, because sub-columns exactly cover their parent's width.

This is how one row shows a single wide label while its neighbour shows two separate values under the same parent column.

A group's span row, whose cell covers all of its rows

A Group's span row is stretched to the full height of the rows inside it and drawn across them. They do not collide because the span row and its rows fill different columns: the span row owns the columns that should read as one tall cell, the rows own the rest.

Design rule for a group: the span row and its rows must declare disjoint sets of columns whose union covers everything the group should show. A column claimed by neither leaves a gap; a column claimed by both is drawn twice.

Widths

Each column's width comes from its ColumnWidthMode:

  • FitContent — wide enough for its widest cell across all rows.
  • Fixed — the width you give it.
  • Fill — shares out whatever is left after the others.

A parent column is at least as wide as its sub-columns combined, and the leftover width is distributed among the Fill ones.

Give at least one sub-column in each group ColumnWidthMode::Fill. If none of them can stretch, they keep their natural widths and may not reach their parent's right edge, leaving a narrow unpainted strip there.

Tags

A Tag is the one identifier in play. On a column it is the name cells use to find it; on a row or a control it is yours to use however you like.

On a columnOn a row or a control
Read bythe blueprint, and columnByTagnobody but you
Purposelets a cell name the columnwhatever you want to attach
Unique?yes, within one gridno requirement at all
Reaches the object?yes, forwarded like any propertyyes, like any property
Column{ Tag{ Col::Level },   // how cells name this column
    Text{ L"Level" }
}

Row{ Tag{ Kind::Channel, channel },   // yours - the grid never reads it
    Cell{ Tag{ Col::Level }, this, &Page::levelCell }
}

Tag packs several values into one, so a column name can be compound: Tag{ SectionId::Audio, Col::Level }. Reading a segment back is tag<index, count, Enum>().

Because one type serves both jobs, nothing stops a cell from naming a row's tag by mistake. The blueprint cannot catch that at compile time; it shows up as an unresolved cell, which a debug build throws on. If a column is meant to be nameable, give it a Tag drawn from the enum your cells use, and keep that enum separate from your row tags.
A column declared without a Tag is legal — it simply cannot be named by a cell. Note that Tag{} holding zero is a perfectly ordinary tag: the first enumerator of a plain enum is zero, so absence is tracked by whether you passed the property at all, not by its value.

Blueprint Reference

import ClaFi.Controls.Grids;
import ClaFi.Controls.Grids_Dt;

using namespace ClaFi;
using namespace ClaFi::Controls;

Grid

template <typename... Args>
Grid(GridBase& grid, Args&&... nodes);

Grid is the root of a blueprint: it describes a whole grid and applies itself to one. Declare it as a member, after the Grid control it builds into:

Grid& m_grid{ body().add<Grid>() };

Grid m_blueprint{ m_grid,
    Columns{ /* ... */ },
    Header{},
    Rows{ /* ... */ }
};
Columns are always applied before rows, whatever order you write them in, because cells resolve their tags by lookup. Rows keep their relative order among themselves, so Header{} written before Rows{} really does come first.
Nothing survives the constructor. Grid has no query members. Columns carry their tags, rows own their cell connections, and both are reachable through the grid itself — see Finding things later. In a debug build the constructor throws if two columns share a tag, or if a cell named a tag no column carries; a release build skips both checks.

Column and Columns

Column{ Tag{ ... }, properties..., Column{ ... }, Column{ ... } }

The Tag names the column and may sit anywhere in the argument list — it is an ordinary property, read by the blueprint on its way through. Everything that is not a nested Column is a property, passed straight through to the grid. Nested Column nodes become sub-columns.

A column without a Tag is allowed — it simply cannot be named by a cell:

Column{ Text{ L"decorative" }, ShowInHeader::Yes }

Columns{ ... } is a grouping node with no effect on the grid; use it as the outer wrapper.

Row, Expander, Group, Header, Span, Divider

Row{ properties..., Cell{ ... }, Control<T>{ ... }, aCellSet }

A Row takes no leading key. Properties — anything that is not a cell — go to the row control, so this is where your Tag goes:

Row{
    Tag{ Kind::Device, deviceIndex },
    Cell{ Tag{ Col::Name }, this, &MyPage::nameCell },
    m_valueCells
}

Every blueprint row can host controls, so nothing special is needed to put one in a cell.

NodeChildren
Row{ props..., cells... }cells
Expander{ props..., rows... }rows, inside the collapsible body
Group{ props..., rows... }rows, overlapped by the span row
Header{ ... }the header of the container it sits in — see below
Span{ ... }the span row of the group it sits in — see below
Divider{}—
Rows{ rows... }spliced into the enclosing grid
Rows{
    Grids::Dt::Expander{
        Header{ Text{ TextStyle::SubHeading, L"Outputs" } },
        Group{
            Span{ Tag{ Kind::Group, Device::Mixer },
                Cell{ Tag{ Col::Name }, this, &Page::groupNameCell } },
            channelRow(Channel::Input),
            channelRow(Channel::Output)
        }
    }
}
Why the node names are unprefixed. The node names are unprefixed because their namespace already says grid: inside Grids::Dt, Row, Cell and Header cannot be mistaken for anything else, and GridRow would stutter. CellWith<T> is a cell as well, named for what the cell holds rather than Control<T>, which would collide with the framework's own control base.

Tag, Text, ShowInHeader and ColumnWidthMode are not grid types at all. They are shared control properties, understood by anything with a column or a header. Header itself is shared too: it lives in ClaFi::Dt alongside OnEvent and Init, because a container having a header is not a grid idea. Span is declared in Grids::Dt, because a row spanning the rows beside it is.

Header

Header{ ... } is the header of the container it sits directly inside. It is not a row and not a node of any hierarchy: a container looks for one in its own argument list, so it can appear anywhere in that list, and a Header nested a level deeper — inside Rows{}, a Row, a Column — is a compile error rather than a silent no-op.

What it accepts depends on the container, because the two headers are different objects:

InThe header isTakes
Gridthe column-title rownothing — the columns already say what belongs in it, through ShowInHeader
Expanderone text controlText. A cell here is a compile error

Span

Span{ ... } is a group's span row: a row of the group's own, sectioned by the same columns as every other row and laid over the group's rows, so its cells span them. It is a part of the container it sits directly inside, the way a Header is, and only a Group takes one — a Span anywhere else, or a Header in a Group, is a compile error. It takes a Tag, cells and CellWiths, exactly as a Row does.

A span being a row means it goes through the same path as every other row: its declared cells answer content authoritatively and stop propagation. Nothing at grid level has to answer for it. It is a RowContainer, so a CellWith lands in one of its cells the way it lands in any row's.
In a blueprint the span's Tag goes inside Span{ ... } and an expander's text inside its Header{ ... } — the nesting says whose each one is. Through the direct API, grid.addGroup takes the span's tag as SpanTag and grid.addExpander the header's text as HeaderText. The standalone Controls::Expander is a different control and takes HeaderText too.

Cell, CellWith, CellSet, Init

Cell{ Tag{ ... } }                        // empty but present
Cell{ Tag{ ... }, lambda }                // void(CellTextArgs&)
Cell{ Tag{ ... }, this, &MyPage::method }  // bound member function
CellWith<T>{ Tag{ ... }, ctorArgs... }  // a live control
CellSet{ cells... }                    // a reusable bundle

The leading Tag on a cell is positional — unlike a column's, it is consumed rather than forwarded, so it has to come first. Everything after it belongs to the control.

CellWith<T> forwards its arguments to the control's constructor. Because the call has to be replayed when the blueprint is applied, those arguments are copied into the node:

Every argument to CellWith<T> must be copy-constructible, and anything large or shared will be duplicated. Wrap it: std::ref(items) passes a reference through instead.

For settings that have no constructor property, use Init<T>. It runs against the control immediately after it is created and can appear anywhere in the argument list:

CellWith<Slider>{ Tag{ Col::Amount },
    ScrollButtons::No,
    Init<Slider>{ [](Slider& slider) {
        slider.setMaxPosition(1.0f);
        slider.setRelativePosition(0.5f, false);
    } }
}

Finding things later

Ask the grid, not the blueprint. Both lookups are on GridBase, so they work whether or not the Grid object still exists:

MemberPurpose
columnByTag(Tag)The Column& carrying that tag. Throws in a debug build if there is none.
findColumnByTag(Tag)Same, but returns nullptr if absent.
forEachRow(func)Calls func(RowContainer&) for every row in the grid and its sub-grids.
Combobox& combobox = row.controlAtColumnAs<Combobox>(m_grid.columnByTag(Tag{ Col::Mode }));

m_grid.forEachRow([this](Grids::Rt::RowContainer& row) {
    refresh(row);
    });

Inside a lambda that runs later, capture the tag and resolve it when the event fires. The columns do not exist yet while the blueprint is being built:

OnEvent{ [this, amountTag](ComboboxChangeEvent& event) {
    auto& row = *static_cast<Grids::Rt::RowContainer*>(event.combobox().parent());
    Control* slider = row.controlAtColumn(m_grid.columnByTag(amountTag));
    slider->invalidateState();
} }
columnByTag walks the column tree; there is no index. That is fine once per event, and wrong in a handler the grid calls per row and per column — an OnCellContent handler, for instance. Resolve the column once, keep the reference, and compare by address there.

Recipes

A label that spans sub-columns

Some rows want one wide label where others want two separate values. Declare the parent column's cell and skip the children:

// Device has two sub-columns.
Column{ Tag{ Col::Device }, Text{ L"Device" },
    Column{ Tag{ Col::Name },    ShowInHeader::No },
    Column{ Tag{ Col::Channel }, ShowInHeader::No }
}

// This row fills the parent, so its cell spans both children: one wide label.
Row{ Cell{ Tag{ Col::Device }, this, &Page::deviceCell } }

// This one fills a child instead, so the two sit side by side.
Row{ Cell{ Tag{ Col::Channel }, this, &Page::channelCell } }

Grouping rows beside a span

A Group's span row stretches down its rows. It is a row, so it is described as one:

// The rows fill Channel; the span row fills Name. Together they cover both.
Group{
    Span{
        Tag{ Kind::Group, Device::Mixer },
        Cell{ Tag{ Col::Name }, this, &Page::deviceCell } },
    channelRow(Channel::Input),
    channelRow(Channel::Output)
}

That is the whole recipe. The span's cells connect to the span row exactly as any row's do, so it answers for itself and nothing at grid level is involved.

A control that belongs to the group rather than to a row

The span's cells are stretched over the rows beside them, so a control in one of them reads as the group's own. That is where a choice made once per group goes:

Group{
    Span{
        Tag{ Kind::Group, Device::Mixer },
        Cell{ Tag{ Col::Name }, this, &Page::deviceCell },
        CellWith<Checkbox>{ Tag{ Col::Mute } } },
    channelRow(Channel::Input),
    channelRow(Channel::Output)
}

The control is placed at the top of the merged cell, at the height of one row, and the column it names counts as the span's under the disjointness rule — no row of the group may declare it.

forEachRow walks the rows of a grid and its sub-grids. A group's span is not one of them, so a control there is not reached that way. Reach it through the group, or keep a reference to it from Init<T>.
This used to need a pair of grid-level OnCellContent and OnGetCellText handlers, filtering on the row's Tag and comparing the column by address, because the blueprint had no way to give the span cells. If you have those handlers, they can go — and check whether their text provider is already the one an ordinary row uses, in which case the span can point at the same method.
The span's Tag is still worth setting even when nothing reads it: hit-testing and your own forEachRow walks use it to tell a span row from an element row.

Rows that differ from their neighbours

Build rows with a function and let it choose:

Row Page::channelRow(Channel channel) const
{
    const bool readOnly = channel == Channel::Monitor;
    return Row{
        Tag{ Kind::Channel, channel },
        Cell{ Tag{ Col::Channel }, this, &Page::channelCell },
        readOnly ? m_readOnlyCells : m_valueCells
    };
}

A row that should leave a slot visibly blank rather than let a neighbour cover it declares the cell with no content:

const CellSet m_readOnlyCells{
    Cell{ Tag{ Col::Mode } },      // present, empty, still bordered
    Cell{ Tag{ Col::Amount } }
};

Reaching a control later

void Page::refreshAll()
{
    for (auto* row : m_blueprint.rows())
    {
        Combobox& mode = row.controlAtColumnAs<Combobox>(m_grid.columnByTag(Tag{ Col::Mode }));
        Slider& amount = row.controlAtColumnAs<Slider>(m_grid.columnByTag(Tag{ Col::Amount }));
        // ...
    }
}
forEachRow visits every RowContainer standing as a row of the grid, including ones inside expanders and groups. Expanders and groups are not containers themselves, so they are stepped over and descended into. A group's span is a container but not a row of the grid, so it is not visited. If some rows do not have the control you are asking for, check the row's Tag first — controlAtColumnAs does not check.

Troubleshooting

Build errors

SymptomCauseFix
Unqualified grid names fail to resolve in an implementation unit A module implementation unit does not inherit everything its interface unit had in scope. Give the .cpp its own imports and using-directives: import ClaFi.Controls.Grids;, import ClaFi.Controls.Grids_Dt;, using namespace ClaFi;, using namespace ClaFi::Controls;. Dt:: needs no alias — it is a real namespace, so it resolves wherever ClaFi::Controls does.
"deleted function" or "no copy constructor", pointing into std::function or std::tuple An argument to CellWith<T> or Column is move-only. The call is stored so it can be replayed, which requires copyable arguments. Wrap it in std::ref. If it truly must be moved, create that control through the direct API instead.
Constraint not satisfied on Cell's constructor The lambda's parameter is not CellTextArgs&. The signature must be exactly void(CellTextArgs&). Watch for a stray const.
Cannot convert const MyPage* in Cell{ key, this, &MyPage::method } The function building the row is const but the cell provider is not. Make the provider const too.
Use of an undeclared member in the Grid initialiser A CellSet, or the grid itself, is declared after the blueprint. Members initialise in declaration order: grid, then cell sets, then blueprint.
Errors listing a control's constructor, from inside CellWith<T> The argument pack does not match that control's constructor. Write one direct row.addControl<T>(column, args...) to confirm the arguments, then move them into CellWith<T> unchanged.

Nothing appears, or it looks wrong

SymptomCause
Debug build throws from Grid's constructor: "Cell keys matched no column" Exactly what it says, and the message lists the numeric key values. Some cell names a column that was never declared with that Tag. Release builds skip the check and silently drop those cells.
A row you declared never appears at all None of its cells resolved, so the row has no content, therefore no height. Same cause as above — run a debug build.
A cell is missing but the row is fine That one tag did not match a column. A debug build throws from the constructor and lists the numeric tag values.
A group's span row has no label The blueprint gives that row no cells, so it answers through the grid's OnCellContent / OnGetCellText handlers. See the recipe.
Every cell is filled in a row you expected to be sparse That row declared no cells, so no handler was connected to it and the question fell through to the grid's event, where hasContent defaults to true. Group span rows do this.
A parent cell is short, with a gap beneath it Something in its sub-columns has content in that row, so it is not merging. Declare the empty sibling as a bare Cell{ key } if you want the space filled.
A narrow unpainted strip at the right edge of a column group None of that group's sub-columns is ColumnWidthMode::Fill, so they do not reach their parent's edge.
Controls appear in the wrong cells A shared CellSet was built with the wrong keys, or a lambda captured a column reference instead of a key.
An event handler no longer recognises a column It resolves the column through the blueprint, which no longer answers lookups, or it resolves a tag on every call instead of once. Keep a Rt::Column& and compare by address: Tag. Compare by address: &event.column() == &m_someColumn, resolved once with columnByTag after the grid is built.

Do / Don't

Do

  • Declare in this order: grid, cell sets, blueprint.
  • Give every column a cell names a unique Tag.
  • Capture tags in lambdas and resolve them through the grid when the event fires.
  • Resolve a column once and compare by address in anything the grid calls per cell.
  • Use std::ref for anything shared or expensive.
  • Use a bare Cell{ Tag{ ... } } when you want a present-but-empty cell.
  • Give at least one sub-column in each group Fill.
  • Run a debug build after changing a blueprint.

Don't

  • Don't draw column tags from the same enum as your row tags — one type serves both, so nothing catches the mix-up at compile time.
  • Don't capture a Column& in a cell set — the columns do not exist yet.
  • Don't keep the Grid around to look things up; ask the grid.
  • Don't call columnByTag inside OnCellContent.
  • Don't assume a Group's span row has declared cells.
  • Don't read a missing cell as an empty one; it means no cell at all.
  • Don't rely on release builds to tell you a tag was wrong.

Appendix · Direct API

The blueprint is a convenience, not a wall. Everything below still works and mixes freely with a blueprint on the same grid, which is useful when one row needs something the DSL does not express.

Without a blueprint, a grid answers two questions through events — which cells exist, and what they say:

grid.onCellContent([](CellContentEvent& event) {
    event.hasContent = /* ... */;   // defaults to true
});

grid.onGetCellText([](GetCellTextEvent& event) {
    event.text() << /* ... */;
});
Note the default: hasContent arrives as true, so without a blueprint every cell exists unless you say otherwise. That is the opposite of a blueprint row, where a cell exists only if you declared it.

The same two events exist on every row, which is how a blueprint answers for the rows it builds. OnCellContent and OnGetCellText are ordinary row properties, and RowBase::onCellContent / onGetCellText connect them later:

grid.addControlRow(Tag{ ... },
    OnCellContent{ [](CellContentEvent& event) {
        event.hasContent = /* ... */;
        event.stopPropagation();   // keep the grid handler out of it
        } });
A row's handler runs before the grid's. If it calls stopPropagation() the grid handler never sees that cell — which is how a blueprint row stays authoritative about its own content while rows it did not declare fall through to whatever the grid says.
