Selection and Focus

ClaFi Framework Developer Manual

All manuals

Introduction

Three things say where the user is in a window, and each is easier to work with once they are apart:

  • The focus is where the keys go. There is one per application, and it moves between windows with the user.
  • The current item is the item a container is on - the page a tab strip shows, the row a list stands at. It stays while the focus is elsewhere, and it is where the focus comes back to.
  • The selection is the set of items a multi-select view holds, on top of its current item.

A control states how it takes part with four answers - NavigationReach, MouseFocus, ClickTarget and FocusScope. What a mouse press focuses, where Tab goes and which item a list is on all follow from them and from the containers the control stands in.

Module Import: 
import ClaFi.Controls.StackView;       // StackView, SelectionMode, DragMode
import ClaFi.Core.Foundation;          // Control, Input, FocusNavigator
import ClaFi.Core.System.UiTypes;      // NavigationReach, MouseFocus, ClickTarget, FocusScope

Basic Usage Example

A page built on Panel, with a tool bar in its head and a list in its body. The page opens with the focus in the list. Tab steps from the list to the tool bar and back, one stop each, and the arrows move inside whichever of them holds the focus.

Panel& topBar = createTopBar<Panel>();

// The tool bar: one stop for Tab, and the arrows move between its buttons.
StackPanel& tools = topBar.createRightBar<StackPanel>(
    Orientation::Horizontal,
    FocusScope::Yes,
    NavigationReach::Yes,
    MouseFocus::Self,
    Spacing{ 4.0f }
);

// The list: it keeps the item the user is on, and holds a selection on top of it.
StackView& files = createBody<ScrollBox>(
    ScrollBars::Vertical
).createBody<StackView>(
    Orientation::Vertical,
    SelectionMode::Multi
);

// A show enters the page at the list, past the tool bar.
setCurrentItem(files);

The rest is the framework's. A mouse click on a file makes it the list's current item, Shift and Ctrl extend the selection, and the list remembers the file it was on when the focus leaves and comes back.

How a Control Takes Part

Four Answers

HitTest picks the control the pointer is over, and four answers say what that control does with input. Each answers one question, and every control has all four.

AnswerThe questionValuesDefault
NavigationReachCan Tab and the arrows land on it?Yes, NoNo
MouseFocusWhat does a mouse press on it do with the focus?Self takes it, Parent asks the parent, Keep leaves it where it is.Parent
ClickTargetIs a mouse press aimed at it, or at its parent?Self, ParentParent
FocusScopeDoes it hold the focus for a current item?Yes, NoNo

The defaults make a label: the keys pass over it, and a mouse press on it is its parent's in every way. The stock controls state their own:

ControlNavigationReachMouseFocusClickTargetFocusScope
A label, a panel, decorationNoParentParentNo
A button, a text box, a check box, a list itemYesSelfSelfNo
A ToolButton - reached by the keys, pressed without moving the focusYesKeepSelfNo
A Tab - reached by the keys, opened by a press without moving the focusYesKeepSelfNo
A tool bar button acting on the editor beside itNoKeepSelfNo
A notice's answer - reached by the keys, pressed without moving the focusYesKeepSelfNo
A part - a slider's thumb, a check box's markNoParentSelfNo
A scroll bar, a splitterNoKeepSelfNo
A menu's frame - its lines carry the focusNoKeepSelfYes
A list, a tool bar, a grid - a container keeping the item the user is onYesSelfParentYes

ClickTarget::Self gives a control press looks of its own, the mouse click, and the scroll a release asks for. A container is what a press lands inside rather than what it was aimed at, so it answers Parent. Any of ClickTarget::Self, NavigationReach::Yes, MouseFocus::Self and FocusScope::Yes makes a control interactive - isInteractive() - and only an interactive control lights up hot and pressed.

A control built with props takes each answer as one of them, and the last one in the pack wins, so a caller names only the answers it changes:

m_answers.add<Button>(
    caption,
    OnEvent{ onClick },
    MouseFocus::Keep   // a Button answers Self by default
);

A control of its own built on Control overrides navigationReach(), mouseFocus(), clickTarget() and focusScope() instead.

Choosing the Answers

Do

  • Give a control the user edits or picks NavigationReach::Yes, MouseFocus::Self and ClickTarget::Self. The stock controls answer so already.
  • Give a button that acts on the focused control NavigationReach::No and MouseFocus::Keep, so pressing it leaves the focus on what it acts on - see Actions.
  • Give a button that stands beside the work and has to be reached from the keyboard MouseFocus::Keep alone. A ToolButton answers so already.
  • Make a container that keeps the item the user is on FocusScope::Yes, with NavigationReach::Yes and MouseFocus::Self. A StackView answers so already.

Don't

  • Leave a button that acts on the focused control in the keys' reach. Tab moves the focus onto it, and its action then resolves to the button itself.
  • Make a container a focus scope when it stands inside one and its items belong to the outer one - see A Container Inside Another.
  • Use a control answering MouseFocus::Keep as a list item. A focus scope makes current and selects only the items a mouse press focuses. Tool buttons made into a list's items say MouseFocus::Self, as TreeItem does. A tab strip takes every tab as its item, so a Tab answers Keep and is still current once pressed.

Parts

A part answers MouseFocus::Parent, so a mouse press on it focuses what a press on its owner would. A slider's thumb, a check box's mark, a split button's strip and a control hosted in a grid cell are parts.

Only the focus is the owner's. A part answers ClickTarget::Self, so the press and the release, the mouse click and the hover and press looks stay its own.

A grid row makes its controls parts. Grids::RowContainer::addControl gives each one ClickTarget::Self, MouseFocus::Parent, NavigationReach::No and FocusScope::No, over whatever the caller passed.

The Focus

One Focus, Two Names

The application has one focus. It leaves one control as it arrives at another, and the other may stand in another window. Input holds it, and all of its members are static.

Input names it twice. focusHolder() is the holder, and focusDelegate() is the control the focus is on. A focus scope holds the focus for its current item, so a list holding the focus has its item as the delegate. Where nothing delegates, both names answer the same control.

The focus is on a path. isFocused() answers true for the delegate and for everything it stands in, so a panel and the window's root read focused while the focus is inside them. At the root of a popup that is up, the path goes on at the control that held the focus when the popup came up - at the item that control answers for - and up from there, through every popup of a stack. Where nothing in that window held it, the path goes on at the control the popup was opened on. A dialog is a window of its own and no part of its owner's path. A control asks about itself with isFocused(), isHovered() and isPressed(). A test for the delegate alone - the row a key applies to - compares with Input::focusDelegate().

Moving It from Code

setFocus() moves the focus to the control, or to its current item where it keeps one. In a list, the control becomes the current item as setCurrentItem makes it - a pick with no modifiers, so a multi-select view's selection becomes that control alone. Focus arriving at the item already current leaves the selection as it is.

The result is the same from any handler. The keys the user holds and the device used last play no part: a container takes the control as a key with no modifier held would bring the focus to it.

A control that cannot take the focus makes setFocus() throw std::logic_error - one that is hidden or stands in something hidden, one whose window is not up, one disabled, and one that answers neither NavigationReach::Yes nor MouseFocus::Self. trySetFocus() moves the focus where the control can take it, leaves it where it cannot, and answers which. It suits a control named some time before the call, which may have been hidden or disabled since.

The focus is only ever on something on screen. Where a window that is built but not yet shown should open is its root's current item - see When a Window Comes Up.

m_editor->setVisible(true);
m_box->setFocus();             // shown a line above, so it takes the focus

if (!origin.trySetFocus())     // hidden or disabled since it was named
    focusContent();

Scrolling the control into view is the caller's - scrollIntoView(). To move the focus the way a show does, into a container at its current item, call FocusNavigator{ form }.enterShown(control). It answers the stop it landed on, or null where the control holds none.

What a Mouse Press Focuses

The first control up from the pressed one to answer Self or Keep settles it. Self takes the focus, and Parent hands the question to the parent. A mouse press on a label inside a tile focuses the tile, and a press on a part focuses its owner - see Parts.

Keep stops the walk with the focus where it was. A tool bar's button keeps the caret in the editor beside it, and so does a notice's answer. A disabled control answering Self hands the press on, as Parent does.

A right click walks the chain the same way, before the menu is raised.

When a Window Comes Up

Every window but a tooltip enters its root as it is shown. The root is entered at its current item, each container on the way by the same rule, and at the first stop in reading order where a container names none - see Where a Show Enters.

Where a window opens is said before it is shown, with makeCurrentItem(). Called on a control with no focus scope above it, it makes the control the root's current item. A message box opens on its first answer this way, and a caller names another one the same way:

MessageDialog dialog{ initiator, L"Write to source", message, MessageIcon::Question };
dialog.add(DialogAnswer::Yes);
dialog.add(DialogAnswer::No).makeCurrentItem();   // opens on No
return dialog.execute() == DialogAnswer::Yes;

setFocus() called before execute() throws, since the window is not up yet.

Escape closes a window that does not hold the root loop, such as a dialog, when it reaches that point in the key order - see Who Gets a Key First. In the main window it goes on to the navigator.

How the Focus Looks

The ring follows the keyboard. A control reached by a key wears the ring, and reads hot while its window has the focus. A control focused by a mouse click wears none, unless Always show focus is on in the application's settings - AppContext::focusAlwaysShown().

Focused is the focus from either device. A caret, the selected-text band and a grid's cell ring read it, so a box focused by a mouse click keeps them while the pointer wanders. The colour rules read these states - see Colour.

A popup takes the focus and leaves the look. The control the focus was on stays on the focus path while the focus is in the popup, so it reads focused with everything it stands in: a text box keeps its caret under its own menu and under one a tool button dropped, and a row whose cell holds an open list keeps its ring. A button that dropped a menu without taking the focus takes none of it, and reads selected while the popup is up - isDroppedDown().

A popup gives the focus back where it found it. As it closes, the focus goes to the control that held it when the popup came up, so a tool button pressed without taking the focus leaves it on the work it was on. Where that control cannot take it back, the control the popup was opened on takes it.

Keys stop at the popup. A key the popup leaves never reaches the control it was opened on - see Who Gets a Key First.

A key landing on a control brings up its tooltip while the keyboard drives, as the pointer resting on a control does while the mouse drives.

Following the Focus in a Control

focusChanged() is told to every control whose isFocused() answer changed, after the move, so the answer it reads is the new one. Override it for something a control does while focused - a caret blinking, a timer running. A control that only looks different needs none of it: its state is invalidated with the move, and its focused factor animates by itself. Opening a popup on a control and closing it again leave that control's chain untold, since it stays on the path.

nestedControlFocusing(FocusEvent&) runs before the move, from the target up to the root. A container brings its items in line there, and may retarget the focus by writing event.control.

Whether the window has the focus is a fact of its own. FormFocusChangeEvent marks each change, and paint reads PaintEvent::windowFocusedFactor.

Keys

Who Gets a Key First

A key goes down this list until one of them takes it:

  1. An open popup, which runs the same list in its own window. A key it leaves goes no further, though the focus path runs on to the control it was opened on.
  2. During a drag, the pressed control and its parents.
  3. The focus delegate and each of its parents, through nestedKeyDown.
  4. A tooltip that is up, for Escape.
  5. The window's shortcuts, then the application's - see Actions.
  6. Escape closes a window that does not hold the root loop.
  7. The navigator, FocusNavigator, which moves the focus.

Return and Space click the focused item when they reach the navigator - the click a mouse click would raise, carrying the key's stamp.

Tab

Tab reads the order the containers keep their children in - the collection, or the slots a container names in navigationSlots. Shift+Tab walks it back. Reading order is all it consults.

Tab leaves a focus scope as a whole. A list, a grid or a tool bar is one stop. Tab entering it lands on its current item, and the arrows move inside.

The window's root and its top layer are one ring. Past the root's last stop Tab goes on into the top layer, and past the layer's last stop it comes round to the root's first. Where the layer holds no stop, Tab comes round within the root. See The Top Layer.

A stop is a control that is shown, enabled and answers NavigationReach::Yes. holdsNavigationStop() answers whether a control is one or holds one.

The Arrows

Each container answers for its own children. The navigator asks the focused item's parent for the child a step lands in - navigationNeighbor. A parent with none hands the step to its own parent, up to the nearest focus scope. The child it names is entered down to a stop - navigationEntry.

  • StackPanelBase - along the lanes, the next item. Across them, the item of the next lane nearest the line.
  • PanelBase - up and down from row to row, sideways along the middle row.
  • A grid - over its cells as a table, and on past its first and last row - see Grid.
  • TreeNode - Right from an open node's header into its rows, and Left from a row back to the header.

A run of steps one way keeps its line. Down from a button and Up again come back to that button, however wide the item between them. Any other move of the focus starts a new run, from the middle of the item it lands on.

Entering a focus scope lands on its current item, whichever way the step comes.

Home, End and the Page Keys

These four address the nearest focus scope. Home and End go to its first and last stop. A page key is as many arrow steps as fit in the view, along the axis the view scrolls on, the item it starts from counted. The view is the one the scope or a box inside it scrolls the item in, and the scope's own otherwise. Where the view shows all the content holds, a page key goes to the end. Outside any focus scope, the focus stays where it is.

A menu's frame is a focus scope for these keys alone. Its lines hold the focus themselves, and its list scrolls inside it, so the page keys page through the list.

Taking a Key

A control takes a key in nestedKeyDown by setting event.handled, which ends the walk before the shortcuts and the navigator see the key. The walk runs from the focus delegate up, so a container sees every key its items leave. Call the base for a key you leave.

A key that moves the focus hands it on with setFocusByKey(target, event.modifiers), a protected call of Control. A list reads the key's Shift and Ctrl as it reads them on an arrow the navigator answers - a range, or the current item moved alone.

void TreeNode::nestedKeyDown(KeyDownEvent& event)
{
    ExpanderHeader& strip = header();
    if (event.key == Keys::Left && event.modifiers.empty() && !strip.isFocused())
    {
        setFocusByKey(strip, event.modifiers);
        strip.scrollIntoView();
        event.handled = true;
        return;
    }
    Expander::nestedKeyDown(event);
}

A Container's Own Navigation

navigationNeighbor(child, step) moves the arrows among a container's children. It answers the child a step from child lands in, holding a stop, or null to hand the step to the parent. The default answers null: a control has to say how its children are placed before a step moves among them.

Control* TreeNode::navigationNeighbor(const Control& child, const NavigationStep& step)
{
    const bool intoRows = &child == &header() && step.direction == NavigationDirection::Right;
    if (intoRows && m_rows.holdsNavigationStop())
        return &m_rows;
    return Expander::navigationNeighbor(child, step);
}
  • navigationEntry(step) answers the child a step from outside lands in. The default is the first child in reading order holding a stop.
  • navigationSlots() names the reading order where it differs from the collection - a container holding its children in named slots. A slot may be unfilled, so an entry may be null.
  • NavigationStep carries the direction, the source - an arrow press or one step of a page press - and the line in form space, with vertical() and forward().

The Current Item

Where a Show Enters

ContainerBase::currentItem() is the item a show enters the container at. When the focus goes into a container as it is shown - its window coming up, or a page control turning to it while the page control holds the focus - it lands in the current item, and at the first stop in reading order where there is none. Each container on the way is entered by the same rule, so a page whose current item is a panel lands inside that panel, at the panel's own current item.

// A show enters the page at its options, past the head.
setCurrentItem(m_optionsBox);

The item is any control inside the container, at any depth, or none, and it is dropped when it is deleted. A window's root takes the item makeCurrentItem() names where no focus scope above the control keeps one - see When a Window Comes Up.

Following the User

A focus scope moves its current item itself, to whatever the user acts on - a mouse click on an item, or the focus arriving from a key - so a show brings the focus back to the item the user left. Any other container keeps the item it was given.

Current is not focused. The item stays current while the focus is anywhere else, and wears its cue, VisualStateIndex::Current, whichever device drives.

A control a mouse press focuses can be current, by default - one that answers NavigationReach::Yes and MouseFocus::Self and is no focus scope itself. CanFocusItemEvent lets a handler answer otherwise:

SingleSelectionStackView& m_harmonyStack{ m_harmonyPanel.createBody<SingleSelectionStackView>(
    Orientation::HorizontalWrap,
    Events{
        [](CanFocusItemEvent& event) {
            event.canFocus = event.item.tag().value == k_harmonyTag;
        }
    }
) };

CurrentItemChangeEvent follows every move, carrying the item that was current before:

m_pageBox.body().onCurrentItemChange([this](CurrentItemChangeEvent&) {
    reportAnchor();
});

makeCurrentItem() makes a control current from code, in the nearest focus scope above it, or in its window's root where there is none. The focus stays where it is; a focus scope holding the focus shows the new item through its delegate. setCurrentItem on the container does the same from the container's side, and on a stack it also scrolls the item into view.

A Container Inside Another

A container inside a focus scope lends its items to it. A grid on a page that keeps the current item is built with FocusScope::No, NavigationReach::No and MouseFocus::Parent. Its rows are the page's items, one selection stands on the whole page, and the arrows travel over every item the page holds.

What the current item leaves is told - nestedCurrentItemChange - so a grid the item has left drops its selected cell.

A shut expander stands for the item inside it. Shut over the container's current item, its header is what the next key moves on from.

Page Controls

The focus goes with the switch. A page control holding the focus enters the page it turns to as a show enters it. A focus elsewhere - in the tab strip, in a sidebar - stays where it is. A mouse press on a Tab leaves the focus where it was, so a focus in the page goes on into the page the tab opens.

Selection

StackView holds a selection on top of the current item, under SelectionMode::Multi. The current item belongs to the stack underneath and follows the keys and plain mouse clicks. The selection belongs to the view. A StackView is a focus scope unless it is built otherwise.

Gestures

GestureWhat it does
A mouse click, or an arrowPicks the item: it becomes current and is the selection alone.
Shift with eitherSelects the range from the anchor to the item. Every pick without Shift moves the anchor.
Ctrl with a mouse click, or Ctrl+SpaceToggles the item.
Ctrl with an arrowMoves the current item alone, for Ctrl+Space to toggle.
A drag from the surfaceSweeps a rectangle over the items it crosses.
A drag from an itemUnder DragMode::EasySelect, starts a rectangle. Under EasyDrag, carries the selection when the item is selected and the item alone when it is not.

Ranges and rectangles reach items in nested panels too.

A mouse press that may become a drag waits for its click. One with Ctrl or Shift may become a rectangle, and one inside the selection may become a drag of the selection. A plain press outside the selection selects at once.

CanSelectItemEvent says whether an item may join the selection - yes in a Multi view for an item that can be current, before any handler. It is asked apart from CanFocusItemEvent, since a rectangle needs answers for items it never makes current.

From Code

files.onSelectionChange([&files](SelectionChangeEvent&) {
    for (Control* item : files.selection())
        mark(*item);
});
  • selection() is the set, with contains() and empty().
  • setSelection(items) replaces the selection with the items that CanSelectItemEvent lets in, and drops the rest without a word - the same test a Ctrl+click or a rectangle passes. The current item stays where it is. In a view that is not SelectionMode::Multi the call does nothing.
  • setFocus() on an item that is not current picks it, and the selection becomes that item alone - see Moving It from Code.
  • A grid moves both with GridBase::selectCell - see Grid.

The Top Layer

A window's top layer stands over its root - FormBase::setTopLayer. The application's notices are shown in one, as cards at the bottom right of the main window.

Tab reaches it after the root - see Tab. A notice leaves the focus where it is when it is posted. Its answers are buttons that answer MouseFocus::Keep, so Tab lands on them and a mouse click on one leaves the focus where the user was.

The focus goes back to the root when the control holding it in the layer is hidden - to the control in the root it came from, or where showing the window puts it when that control is gone. A notice answered from the keyboard hides its card, and the focus returns to where the user was.
