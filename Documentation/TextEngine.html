ClaFi TextEngine

One string, a list of markers, and a layout somebody else already built

Introduction

A Text is a plain string and a list of markers, each marker a position and one formatting item. It carries no fonts, no colours and no geometry - a marker says push bold here or this run is drawn in the accent, and what those mean is settled later, by the control that draws it and the theme in effect at the time.

That is what makes a Text cheap to build and safe to keep. Building one every paint is the normal way to use it: the shaping is cached behind the engine, and a rebuilt Text that says the same thing hits that cache.

Module imports: ClaFi.Core.TextEngine.Text for Text, ClaFi.Core.TextEngine.Types for the formatting items and TextStyle, ClaFi.Core.TextEngine.Fmt for the format-string syntax, and ClaFi.Core.TextEngine for the engine that draws and measures. Colours come from ClaFi.Core.System.InkWell - see the Colour manual.

Quick Start

Two spellings of the same thing. The stream is for text assembled from parts; the format string is for text whose shape is known and whose values are not.

// The stream.
Text text;
text << TextStyleId::Section << L"Performance" << PopTextStyle{} << TextOp::EndLine
     << InkWell::textInk(InkGrade::Muted) << L"Frames: " << PopColor{}
     << InkWell::accentInk() << frameCount;

// The format string. Both syntaxes in one: [tag] formats, {} takes an argument.
Text same{ Fmt{
    L"[section]Performance[/section]\n"
    L"[color muted]Frames: [/color][color accent]{}[/color]",
    frameCount } };

Building Text

The stream

Everything is streamed in with operator<<. The variadic constructor is the same sequence written as one expression, which is what makes a Text usable as a control property.

operator= takes any one of the same arguments and states the whole text rather than adding to it. Assigning one Text to another copies or moves it, so a text is an ordinary value to hold in a member or hand back from a function.

Text caption;
caption << L"Opening ";                 // adds
caption = L"Ready";                     // replaces
caption = other.selectedText(range);    // moves
caption = Text{ InkColor::Accent, name, L" saved" };   // several parts

An assignment operator takes exactly one argument, so a text built from several parts is spelt as a Text and moved in, as the last line shows.

The constructor stays explicit. It accepts any argument list at all, so an implicit one would offer a Text conversion from every type in every overload set it appears in. Name the type where a Text is built - Text{ L"Ready" } - and assign without it.

PlaceHolderText and TooltipText are Text under another name, so a control can tell which of its texts it was handed by the type alone.

Fmt and arguments

Fmt holds a format string and a reference to each argument. Text{ Fmt{ ... } } builds a text from it; text << Fmt{ ... } appends to one that exists.

The format string carries two constructs, and the difference between them is whether they consume an argument:

ConstructConsumes an argumentMeaning
[tag]NoChanges the stream state - a style, a colour, a space, an alignment.
{}, {:.2f}, {:02X}YesFormats the next argument through std::vformat, with the spec written inside the braces.
[color {}]YesThe bridge between the two: takes a Color argument and pushes it.
[icon {} 24,24]YesTakes a paint callable and places it inline.
\nNoA literal newline in the format string is a line break, the same as [n].

Arguments are consumed strictly in order by whichever construct takes one, so an [icon {}] and a {} draw from the same queue. A construct that wants an argument when none is left is dropped rather than diagnosed.

Text{ Fmt{
    L"[icon {} 18,18][b]{}[/b] [color muted]{:.1f} ms[/color]",
    paintDot,        // 1 - the icon
    name,            // 2 - the bold run
    elapsed } };     // 3 - the number
An argument's type picks its handler. Integers and floating point go through std::vformat; a Color prints as text under {} and pushes as a colour under [color {}]; anything callable with a PaintIconEvent& is an icon painter. Everything else is streamed as it stands.

Tag Reference

Typography

TagStyleDrawn as

Each tag is the style's TextStyleId member in lower case, and is short for [style title] - the spelling a document writes. Either form reads.

The two families are generic - GenericFamily::sansSerif and GenericFamily::monospace - and each platform resolves them to a face of its own: DirectWrite is handed Segoe UI and Consolas for them, fontconfig reads both names as the aliases its configuration defines. A concrete family named with [font] is passed through as written and stands or falls on the fonts installed.

A style closes with its own name or with [/style]; either pops the style opened last. Inside a style, three more pairs override one property at a time:

TagEffect
[b] [/b], [i] [/i]Weight and slant.
[sup] [/sup], [sub] [/sub]A run off the baseline. Either closer ends the nearest script still open.
[size 24] [/size]Font size in design pixels.
[font Consolas] [/font]Font family by name.
[n], [end]End the line. Interchangeable, and the same as a literal newline.
[left], [center], [right], [justified]Alignment of the paragraph the tag lands in.

A script takes the size of what it stands on down by a fixed factor and steps the baseline by a share of that size, so [sup] inside [sup] shrinks and steps again - 2[sup]2[sup]n[/sup][/sup] comes out as a tower of three sizes. One stack holds both kinds, which is why [/sup] and [/sub] are one instruction: each ends the nearest script still open.

The line is not made taller for a script. A raised run keeps inside the ascent of the run it stands on; a lowered one whose letters descend can reach below what its line was measured at.

Colour

A colour tag names an ink - an InkColor at an InkGrade - and states no tone of its own; the tones are InkWell's. Both are spelt as their members in lower case, the colour first, and either can be left out: the colour is then text and the grade strongest.

[color muted]textInk(InkGrade::Muted) - secondary text.
[color accent]accentInk() - the colour the interface answers with.
[color spot]spotInk() - the second accent, for what stands apart from the interface.
[color green], [color blue], [color red]The semantic inks of those names.
[color red muted]A colour at a grade. The colours are text, accent, spot, yellow, green, blue, red, black and white; the grades are faint, subtle, muted, strong and strongest.

[color #4EC9B0]A colour stated outright. The theme does not touch it.

Yellow is drawn, not read. At the 4.5:1 reading threshold on a light page the whole warm arc collapses to brown, so no yellow is both legible and recognisable. Use InkWell::Yellow on an icon and let the text say it in words. [color yellow] reads, so that a text built from code can be written out and read back.

Icons

An icon in text is a PaintIconFunc - anything callable with a PaintIconEvent& - given a box in the flow. The tag takes the painter from the arguments and the box from its own text:

WrittenBox
[icon {}]16 × 16, baseline at 85% of the height.
[icon {} 24]24 × 24.
[icon {} 24,20]Width 24, height 20.
[icon {} 24,24,20]Width, height, and baseline stated outright.

The painter is handed an event that answers everything a control's paint event does about colour: event.ink(...), event.textColor(), event.iconRect(), event.scaleF(...). An icon of width 0 draws outside the flow without occupying it, which is how a bullet is made.

Links and anchors

A target is read up to the closing bracket, so one holding a ] cannot be written in a format string. Stream a PushLink for it instead; a document and the clipboard carry it whole.

In a document

A Text in a document is its plain text and one entry per marker, and each marker is written as the tag Fmt reads for it. Import ClaFi.Core.Dom_TextSerializers wherever a blueprint states a Text, and Dt::Value{ L"Caption", Text{} } holding [title]Title[/title] and [color muted]note[/color] writes as

Caption=[
    Markers=[
        =[
            Tag=style title
            At=0
        ]
        =[
            Tag=/style
            At=5
        ]
        =[
            Tag=color muted
            At=10
        ]
        =[
            Tag=/color
            At=14
        ]
    ]
    Text=Title and note
]

At is the index in the plain text the marker applies from, and each child is found by name, in any order. A style is written as style and its name. An ink is written with its colour and its grade, each left out where it is text or strongest; the text ink at strongest is written color strongest. Every spelling in the tables above reads back, the style shorthand included.

An icon's painter is a callable and is not written. It reads back at its stated extent and draws nothing.

Worked Examples

Flexible space

Text{ Fmt{
    L"[color muted]System[/color][flex][b]ONLINE[/b]\n"
    L"[color muted]Ping[/color][flex]{} ms",
    ping } };
SystemONLINE
Ping24 ms

Each line's flex space eats whatever that line has left over, so the right-hand column is flush against the right edge and ragged against the left. That is the difference from a tab stop, and the reason both exist.

Tabular alignment

Text{ Fmt{
    L"[b]Component[/b][tabto 150][b]Status[/b][tabto 260][b]Load[/b]\n"
    L"Parser[tabto 150][color green]Active[/color][tabto 260]High\n"
    L"Renderer[tabto 150][color muted]Standby[/color][tabto 260]Low" } };
ComponentStatusLoad
ParserActiveHigh
RendererStandbyLow

A tab stop is an absolute x inside the block, so every row lands on the same column whatever the width the block was given. Text that has already passed a stop does not go back to it.

A tab character in the text is the other kind of stop: it reaches the next multiple of four spaces of the font the paragraph starts in, so in a monospace font a tab is four columns.

Bullets and inline icons

auto paintBullet = [](PaintIconEvent& event) {
    FloatPoint center = event.iconRect().center();
    // The icon has no width, so the centre sits on the indent - shift it into the margin.
    center.x -= event.scaleF(16.0f);
    event.canvas().fillCircle(center, event.scaleF(3.0f),
        InkWell::accentInk().toColor(event));
    };

Text{ Fmt{
    L"[indent 34]"
    L"[icon {} 0,18][b]Lambda drawables:[/b] [color muted]any callable renders into the flow.[/color]\n"
    L"[icon {} 0,18][b]Reusability:[/b] [color muted]pass one painter as many times as you need.[/color]"
    L"[indent 0]",
    paintBullet, paintBullet } };
Lambda drawables: any callable renders into the flow.
Reusability: pass one painter as many times as you need.

The same painter passed twice draws twice - the argument is read, not consumed destructively - so a list of any length costs one lambda and one argument per row.

Drawing and Measuring

The engine builds the layout. A control hands it a text, a rectangle, the colours it resolved, and where in that rectangle the text block belongs:

DrawTextResult drawText(ControlPaintContext&, const FloatRect&, const Text&,
    TextAnchor, const EditProps* = nullptr, TextRenderMode = TextRenderMode::Static,
    bool wrap = true);

CalculatedDimensions calculateText(const FormContext&, const Text&,
    MaxSize = { k_maxFloat, k_maxFloat }, bool editable = false, bool wrap = true);

Colours arrive with the draw. A run names inks, and the paint context the draw is handed is what resolves them - so the same layout draws correctly through whichever backend owns the form it appears in.

Always pass the anchor. A layout is built at the origin of a box of the given size, and the anchor is the whole of what says where in the bounds that box was put. A call that leaves it out draws against a box the text does not occupy.

TextRenderMode is a question about movement, not about quality:

ModeFor
StaticText that cannot move. Everything that makes a glyph crisp, because nothing will ask it to be anywhere else.
MovableText that can move, while it is not moving. It gives up the crispness permanently rather than at the moment movement starts - every setting that buys crispness ties the raster to sub-pixel position, so switching it around a movement makes the text visibly change at both ends, at rest.
MovingWhile the position is actually changing: outlines filled as geometry instead of a glyph rasterized afresh each frame. That is the expensive half, so it is not paid by a control that is merely capable of moving.

Passing an EditProps makes the layout editable, which is a property of the text and not a convenience: an editable text keeps the empty paragraph a trailing newline opens, because the caret has to be able to stand on it. Measured as not editable, that row is missing from the size the control is given.

Positions in a text are answered without a layout at all - nextWord, prevWord, wordAt, paragraphAt. A caret is measured on a TextLayout by whoever holds one, because an edited text is a different text on every key, and routing that through the shared cache would store a copy per press. A paragraph range includes the newline that ends it: a selection that leaves it behind cuts the text and leaves an empty row where it was.

A text box holds the layout it draws from rather than taking one from the cache. Its paint, its caret and every position it measures run on that one layout, so a caret is never read off one build and drawn on another.

A control that holds its own layout

When a control needs one

WithTextLayout<HostClass> gives a control a TextLayout of its own to shape in, instead of drawing through the engine's cache. It is spelt in the base list and nowhere else:

class TextBox : public WithTextLayout<Label>

// A label that rewrites its words needs nothing of its own:
using CaretReadout = WithTextLayout<Label>;
Using it is the declaration. A control whose text changes often derives from it, and a control whose text is written once and then stands does not. The base list says it once, and nothing else has to be kept in step.

The cache is addressed by what a text says, which is what lets a hundred buttons saying one word share a single shaping. It is also what a text rewritten every frame misses on every paint - the value under a slider's thumb, a frame rate, a caret position in the corner of a scroll box. Each new value takes a fresh entry and pushes out a layout that was being shared, so a drag of a few seconds empties the cache and leaves every label on the form to be shaped again.

A control here shapes its own text in place: no hash, no comparison against another control's words, nothing evicted, and nothing of its own in there to be evicted from. Editing is the second reason and the section above states it - an edited text is a different text on every key, and the paint and the caret have to read one build.

The two seams

Two virtuals on Control decide which layout an answer comes out of, and they are a pair:

virtual DrawTextResult drawText(PaintEvent&, const FloatRect& textBounds, const Text&);
virtual CalculatedDimensions measureText(AlignEvent&, ScaledDimensions asked, const Text&);

Everything around them stays with the framework. paintText keeps the rect, the gather and the flags the result raises; calculateText keeps the gather, the rule that a run which does not wrap is measured against no width at all, and the clamp to the box.

Override both or neither. A control that replaces one measures on one layout and draws on another.

Bringing the layout up to date

Both seams, and everything else that asks the layout a question, go through one call - which is what keeps a position from being read off one build and drawn on another:

TextLayout& syncedLayout(const FormContext&, const FloatRect& textBounds) const;
TextLayout& syncedLayout(const FormContext&, const FloatRect& textBounds, const Text&) const;

virtual void takeText(const Text&) const;

The one-argument overload gathers a text itself, the way a paint does. Asking twice is free: a gather names a control's own text rather than copying it, so an answer that is that object is recognised by address, and an answer with no life of its own - one a parent composed, or a handler built - is compared instead. Either way an unchanged text rebuilds nothing, and a control measured four times in one pass shapes once.

Only the size of the rect is taken. Where it sits is the caller's business and the anchor's, so a control carried sideways under a viewport does not rebuild for every pixel it moves.

A layout held here stands outside the cache, so it answers invalidateLayouts() for itself: it compares layoutGeneration() against the number it was built at, and invalidates when the two have parted.

takeText states the whole of a text the layout has not been told about, which is what a text rewritten from nothing needs. A host that knows what changed overrides it and says so instead - see Editing a layout in place.

Positions on a held layout

Whoever holds a layout asks it where things are. The word-level questions above need no layout; these do, because the answers are about lines, and lines exist only once a text has been broken to a width.

CallAnswers
caretPos(FloatPoint)The CaretHit a point names: an insertion position, and the affinity that says which of two rows a position on a break belongs to.
getCaretRect(CaretHit)Where that position stands.
posOnNextRow(CaretHit, ScrollDirection, targetX)The position one row up or down. targetX is the column a run of arrow keys is holding, so a short row passed through does not pull the caret in with it.
rowStart(CaretHit), rowEnd(CaretHit)The two ends of the row the position stands on - where Home and End go.
lineColumnAt(size_t)Which line the position is on and how far into it.
struct TextLineColumn { size_t line{ 1 }; size_t column{ 1 }; };
A row is what the breaker made; a line is what the newlines cut. So a row moves with the width the text was broken at, and a paragraph broken across five rows carries one line number, the column running along the whole of it. Both are counted from one, which is what a reader counts from.

lineColumnAt is a binary search over the paragraphs and reads no text, so a status readout can ask it on every key press of a fifty-thousand-line document. The row calls walk the paragraphs, which is the cost of an answer that depends on where the lines were broken.

All of these are in the layout's own coordinates - the box is built at the origin. A control crosses anchoredOrigin in both directions: subtracting it from a point handed in, adding it to a rect handed back.

Editing a layout in place

A layout is normally told a whole text. A caller that knows what changed can say so instead, and then a paragraph the edit did not reach keeps the shaping it already has:

struct TextEdit { TextRange replaced; size_t insertedLength; };

[[nodiscard]] bool applyTextEdit(const Text&, TextEdit);
[[nodiscard]] TextEdit mergedEdits(TextEdit first, TextEdit second);

The edit is stated in the coordinates of the text before it. What the layout does with it is find the paragraphs it reaches, re-shape those, and move the rest: their characters begin later or earlier, and their lines stand lower or higher. Typing a newline, deleting one and pasting a thousand lines are all the same operation - how many paragraphs the slice became is read off the rebuilt text rather than worked out from what the edit was.

It can decline, and the answer says so. A layout with nothing shaped yet, or a paragraph in the slice that is not leading while the box it stands in has moved. A caller that gets false states the whole text with setText; the layout is already invalidated for it.

One record carries one edit, and key repeat outruns the paint loop - so several edits can reach the text before anything asks the layout about it. mergedEdits folds a second into a standing record, answering the hull of the two. A hull can name text neither edit touched, which costs a paragraph re-shaped that did not have to be, or a refusal - never a wrong answer.

A caller must also know that the record describes this text. What makes an edit and a text one story is that the lengths agree: the text the layout holds, plus what the edit inserted, less what it replaced. A control whose text arrives from its parent edits its own, and the two are not the same text.

Links and Anchors

A link is a run of text that points somewhere, and an anchor is a run of text a link can point to. Both are pairs of markers, the way bold is, so they travel through every edit, copy and paste the rest of the formatting does. What a link does is up to the control holding the text: a TextBox follows it, and a label draws it and nothing more.

Writing a link

Text{ Fmt{
    L"See [link https://example.com]the site[/link] or "
    L"[link #gallery]the long gallery[/link]." } };

// The same link, streamed.
Text text;
text << L"See " << PushLink{ L"https://example.com" } << L"the site" << PopLink{};
See the site or the long gallery.

The target is any string at all - a URL, a path, # and an anchor name, or a word the application answers for itself, such as clafi:ledger. The engine never reads it.

A link is drawn in the accent ink. A colour pushed before the link opened gives way to it; one pushed inside the link is the link's own, which is how a link that should not look like one is written. The underline is not part of the text: the control underlines the link under the pointer when a click there would follow it, as the second link above shows, and draws nothing under it otherwise.

The underline stands clear of the ink it would cross, the way a browser's does: it is cut where a descender reaches through it, with a gap of its own thickness on either side - see The link underline.

Anchors

L"[anchor clue-17][b]Clue 17.[/b][/anchor] Dmitri stands two doors from whoever was counting."
// ... and anywhere in the same text:
L"The blue landing is settled by [link #clue-17]Clue 17[/link]."

An anchor is a run rather than a point: it holds text, and a box going to it selects that text. It draws nothing. Where two anchors share a name the first in the text is the one reached, and one left open runs to the end of the text.

Text::anchorRange(name) answers the range an anchor holds, or nothing where the text holds no anchor of that name. It walks the markers when it is asked: an anchor is looked for when a link to it is followed, and nothing is kept for it in between.

Links in an edited text

A link does not grow at its end. A character typed after a bold word is bold, and every other run takes in what is typed at its end the same way. A link is the exception, because a word typed after it is not part of where it points. Typing over the end of a link is different: the text replaced was the link's, and what replaces it is too.

Two links that meet and name one target are one link. They are pointed at, underlined and followed whole, and what is typed where they meet goes inside. An undo that puts a link's last word back produces exactly such a pair, so the link it restores behaves as it did.

An anchor grows at its end the way bold does, since what is typed there is part of what it holds. Deleting the whole of a link or an anchor takes its markers with it, and an undo puts them back.

Following a link in a TextBox

BoxFollows a link onA plain click on a link
Read-onlyA clickFollows it.
One the user types intoCtrl+clickPlaces the caret, as it does anywhere else in the text.

The same rule decides when a link is underlined and shows the hand pointer, so what stands under the pointer always says what a click there will do. A press that ends in a selection was a drag, and follows nothing.

Where a followed link goes, in order:

  1. #name, and the box's own text holds that anchor - the box goes to it. The anchor's text is selected and its line brought to the top of the view, the way a browser lands on a fragment. No event is raised.
  2. Any other target - OnLinkClick is raised with it. A handler that answers the target stops the event.
  3. Nothing stopped it - a target starting with http:, https: or mailto: is opened through the shell, whatever the case of its letters. Every other target goes nowhere.
box.onLinkClick([](LinkClickEvent& event) {
    if (!event.target.starts_with(L"clafi:"))
        return;
    openPage(event.target.substr(6));
    event.stopPropagation();
    });

LinkClickEvent carries target, as the text states it, and stamp, the press that followed the link. A #name the box's text does not hold is raised like any other target, which is how a link reaches an anchor on another page: the handler opens that page and calls goToAnchor on its box.

The shell opens three schemes and no more. A text can come out of a file or off the clipboard and name anything, and the shell runs a program it is handed. A file: link, a path or a scheme of the application's own does nothing until a handler answers it.

Back and forward

// false, and nothing moves, where the text holds no such anchor
bool goToAnchor(std::wstring_view name);
void goBack();
void goForward();
bool canGoBack() const;
bool canGoForward() const;

Every jump is remembered. Before it goes to an anchor the box keeps where it stood - the selection, and the position the view showed at its top - and Alt+Left goes back to it, Alt+Right forward again, the way a browser's history does. goToAnchor is what records a place, whether a link called it or the application did. With nothing to go back or forward to, the key is left unhandled and reaches whatever stands above the box.

An edit made through the box moves every remembered place with the text, so going back after typing lands where the user was. An undo or a redo drops the history. A text the host writes leaves it standing, and a place past the end of that text is held to its end when it is gone to.

Link hints

Every link has a hint, whether a click would follow it or not: the underline says a click would, and the hint says where it goes, which a reader wants in a box they type into as much as in one they read. It stands over the line the pointer is on, starting where the link starts on that line, so it covers neither the link nor the words around it. Where the screen has no room above the line, it stands under it. While the pointer is on a link, the link's hint stands in for the box's own.

What the box writes when nothing else does:

In a box the user types into, a muted line follows: Ctrl+click to follow. A plain click there places the caret, and nothing else on screen says the link can be followed at all.

OnGetLinkTooltip is raised first. Its event carries target, range - the text the link covers - and tooltip, the hint itself with its placement and anchor already stated. What a handler writes into tooltip.text is the whole of the hint, and the box then writes nothing.

box.onGetLinkTooltip([](GetLinkTooltipEvent& event) {
    if (event.target.starts_with(L"clafi:"))
        event.tooltip.text << L"Opens the " << event.target.substr(6) << L" page";
    });
A hint breaks its lines at 480 design pixels, and its window is sized to the widest line it came to - so a short hint stays short, and a long one wraps rather than running out to the edge of the screen. That holds for every hint in the framework except one standing over a control's own text, which repeats the lines that control broke. A preview is cut at six lines of that width.

Links on a held layout

A control drawing links of its own - one that holds its own layout - asks the layout which link is under a point, and tells it which one to underline:

[[nodiscard]] std::optional<LinkHit> linkAt(FloatPoint);
void setHoveredLink(TextRange);     // an empty range underlines nothing
TextRange hoveredLink() const;

struct LinkHit { LinkSpan link; size_t pos; };   // the link, and the character under the point

linkAt takes a point in the layout's own coordinates, the ones caretPos takes. A hit test names the nearest character even past the end of a line, so the point is held to the box that character's glyph stands in: past the end of a line, between two lines or below the text, there is no link. pos is the character under the point, which says which line of a wrapped link the pointer is on.

The hovered link is a draw-time question, the way colours are: stating one shapes nothing, and the caller repaints. A new text drops it, since the range was stated in the text it was found in.

LinkSpan is TextSpan<std::wstring_view> - the range a link covers and its target - and BakedText::links() answers every one in text order. The target is a view into the text the spans were baked from, and holds while that text stands unchanged.

Do and Don't

Do

  • Build a Text per paint. An identical text hits the layout cache, so rebuilding costs a hash and a compare.
  • Name inks, not colours, so a run keeps its meaning through a theme change.
  • Use [tabto] for columns and [flex] for two ends of a line. They answer different questions.
  • Pass the anchor that matches how the control positions its text.
  • Give an icon a Tag when one painter serves several rows and has to tell them apart.
  • Answer your own link targets in OnLinkClick and stop the event. Of the rest, the box opens only http, https and mailto.

Don't

  • Don't hold a Text to avoid rebuilding it unless it is genuinely expensive to assemble - the cache is behind the engine, not in your control.
  • Don't count on an unmatched tag failing loudly. An unknown [tag] and an {} with no argument left are both dropped in silence.
  • Don't mix argument order between the two syntaxes. There is one queue, and [icon {}] draws from it too.
  • Don't reach for [color #RRGGBB] in a control. A literal colour is right for art and wrong for interface.
  • Don't measure editable text as static and then draw it editable. The two answer different heights.
  • Don't put a text that is rewritten as the user watches through the cache. A control whose words change often derives from WithTextLayout and shapes them in place.
  • Don't write a link target holding ] in a format string. The tag ends there; stream a PushLink instead.

How It Works

Markers to spans

BakedText::rebuild walks the markers once and turns a stack-based description into absolute ranges: ColorSpan, WeightSpan, StyleSpan, SizeSpan, FamilySpan, ParagraphStyle, a LinkSpan for every link, and a BakedInlineObject for every icon, flex space and tab stop. That is the form the native layout is fed.

A colour span holds ColorDef, which is std::variant<Ink, Color> - the name of a colour rather than a colour. Colours are deliberately absent from what a layout is built from: they reach the native layout when it is drawn, so a theme change re-draws the same shaping rather than paying for it again. Alignment is absent for the same reason: where finished lines sit inside their box is set on a built layout, not shaped from.

The layout cache

The engine keeps up to 512 layouts, keyed on a text rather than on a box: the text's hash, the scale factor, whether it is editable, and - for a text carrying a flex space - the event phase. A flex space is the one thing laid out differently for a measurement and for a paint, filling the box it is drawn in and contributing nothing to a size. Floats are held as their bits, because this is an identity question and not a numeric one.

A key names a bucket, and the bucket holds one layout per width the text has been broken at. Lines broken at one width came out no wider than the widest of them, and every width between the two breaks them the same way - none has to split, each already fitting, and none can join, because the breaker refused the next word at the wider of the two. So a layout is asked whether it accepts the width being requested, and the first that does answers it. That is what lets one build serve both passes: a control is sized to what it measured, so the paint asks at a width inside the interval of the build the measurement just made. A width outside every interval takes a layout of its own, up to four to a text, and the least recently used of them goes.

The box a layout stands in is not the width its lines were broken at. A native layout places a centred or right-aligned line at an offset measured from the box it was told about, so a shaping answering about a narrower box is told so before it is drawn or measured. Only the placement moves: the box is never wider than the width the lines were broken at.

The height is in none of this. It decides which line the text is cut off at and which lines fade, and that is read off the finished lines - so a box of another height keeps the shaping and reads the fit again.

A hash is a way to find an entry, not proof it is the right one - two texts landing on one would draw the wrong words - so a hit is confirmed by comparing the Text itself. The cache owns that copy, because every caller's text is a temporary built for one paint while the layout keeps a pointer to the one it was given.

Text::hash stands in for the whole Text, colour markers and all. A colour is no part of a build, but it is part of what makes one Text a different Text, so two runs naming different inks hold a cache entry each rather than sharing a key and evicting one another on every alternation. For anything that changes what a build would produce without being part of the key - the font table above all - invalidateLayouts() drops the cache and moves layoutGeneration() on, and a layout held outside the cache compares that number against the one it was built at.

Paragraphs on cells

A paragraph set in one monospace font is not shaped at all. Every glyph of such a font is one cell wide, so the x of a column is the column times the cell, a tab reaches the next multiple of four columns, the line is one row of the face's height, and a hit test is a division. The layout decides this per paragraph, before building anything: one font over the whole of it - a span of family, size, weight or style ending inside the paragraph makes a paragraph in two fonts - no inline object, no script, not justified, and every character either a tab or one the font has a glyph for at exactly the cell advance. A paragraph that qualifies is one row of columns times cell and holds no native layout. Anything else is shaped natively, that paragraph alone: one line of Arabic in a source file costs that line and no other.

What this buys is the shaping. A document of source is one pass over its characters instead of a native layout per line, and what the layout keeps is a paragraph record per line rather than a native object each - the lines of every paragraph live in one pool on the layout, so a document of a hundred thousand rows allocates once for them. The pixels are the ones the native layout would draw: DirectWrite's natural measuring mode already places a monospace run at column times advance, the tab stops are the same four cells, and the glyphs reach the same draw primitive - DrawGlyphRun on Direct2D, the glyph cache and the compositor on the CPU backends. The cell and the line height are the platform's own measurement of the font, the same one the tab stops are read from.

One glyph per character. A paragraph on cells draws each character as its own glyph, so a font's ligatures are not applied to it. Consolas and DejaVu Sans Mono carry none; Cascadia Code and Fira Code do, and a text set in one of those shows its characters unjoined.

What a glyph table alone cannot lay out stays native, and the layout refuses it without asking the font: the controls and the format characters, combining marks, the right-to-left scripts, the scripts that reorder or stack, and anything past the basic plane. A wrapping layout keeps a paragraph on cells while its ink fits the width it breaks at - a line that fits is never broken - and hands one that does not to the native layout. Left, centre and right alignment are an offset inside the box, applied as the paragraph is drawn or hit rather than told to a layout, so a box that moves costs nothing.

Nothing in the API says which paragraphs are on cells. [code] text, a CodeBox, a HexView line and a label in a monospace family all take the path when they qualify, and a caller reads the same positions and draws the same pixels either way.

The link underline

The layout draws the underline of the hovered link: one segment per line the link reaches, under the glyphs that line shows, in the colour the segment's first glyph was drawn in. It stands below the baseline by a share of the room the line has there, in the thin stroke; the font's own underline metrics are not read. It is drawn over the glyphs, so a selection band does not cover it, and it does not fade with the glyphs of a line the box cuts.

Where it would cross ink, it is cut. The native layout answers where the link's glyphs put ink between the line's top and bottom edges - INativeTextLayout::appendInkAcross, and INativeMonoFont::inkAcross for a paragraph on cells - reading the same glyph coverage the CPU path draws from, a row at a time, and counting a pixel as ink past a fifth covered. Each stretch is widened by the line's thickness on both sides and cut out. A piece left no longer than the line is thick is not drawn, since it would read as a dot between two descenders. On Direct2D the glyphs of a hovered link are rasterized into the CPU glyph cache for the purpose.

Nothing is kept. The ink is asked for on every paint while a link is hovered, and that is a line or two of one link.
